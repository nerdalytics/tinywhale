## 2. Interfaces and worlds in 0.3 and differences from 0.2 (incl. `wasi:cli/command`)

### Takeaway
0.3 keeps `wasi:cli`, `wasi:http`, `wasi:filesystem`, `wasi:sockets`, `wasi:clocks`, `wasi:random` and deletes `wasi:io` outright: pollables become `future<T>`, input/output streams become `stream<u8>`, and start/finish/subscribe triples become `async func`. `wasi:cli/command` exports `run: async func() -> result`; stdout is written by handing the host the readable end of a `stream<u8>` and getting back a `future<result<_, error-code>>`.

### Cited Findings
- Packages: `wasi:cli`, `wasi:http`, `wasi:sockets`, `wasi:filesystem`, `wasi:clocks`, `wasi:random`; "There is no WASI 0.3 version of `wasi:io`." Worlds: `wasi:cli/command`, `wasi:http/service` (replaces `wasi:http/proxy`), `wasi:http/middleware`; plus `imports` worlds per package. `wasi:tls@0.3.0-draft` is a draft (initial support added in Wasmtime 44). — [wasi.dev/releases/wasi-p3](https://wasi.dev/releases/wasi-p3)
- Mapping from 0.2: `pollable` → `future<T>`; `input-stream`/`output-stream` → `stream<u8>`; `poll` → await on a future; `start-foo`/`finish-foo` → `foo: async func(...)`. — [wasi.dev/releases/wasi-p3](https://wasi.dev/releases/wasi-p3); [bytecodealliance.org/articles/WASI-0.3](https://bytecodealliance.org/articles/WASI-0.3)
- Design shift: in 0.2 each component had its own event loop; in 0.3 "the host is now the one in charge of managing the one event loop that is shared by all components." The async model is completion-based (io_uring/IOCP-like) rather than readiness-based. — [bytecodealliance.org/articles/WASI-0.3](https://bytecodealliance.org/articles/WASI-0.3)
- Stream-plus-future pattern, e.g. 0.2 `read-via-stream: func() -> result<input-stream, error-code>;` vs 0.3 `read-via-stream: func() -> tuple<stream<u8>, future<result<_, error-code>>>;`. — [bytecodealliance.org/articles/WASI-0.3](https://bytecodealliance.org/articles/WASI-0.3)
- `wasi:cli@0.3.0` `command` world (verbatim, minus annotations): `world command { include imports; export run; }`. — [command.wit @ v0.3.0](https://github.com/WebAssembly/WASI/blob/v0.3.0/proposals/cli/wit/command.wit)
- `interface run { run: async func() -> result; }` — [run.wit @ v0.3.0](https://github.com/WebAssembly/WASI/blob/v0.3.0/proposals/cli/wit/run.wit)
- stdio interfaces (verbatim signatures): `interface types { enum error-code { io, illegal-byte-sequence, pipe } }`; `stdin.read-via-stream: func() -> tuple<stream<u8>, future<result<_, error-code>>>;` `stdout.write-via-stream: func(data: stream<u8>) -> future<result<_, error-code>>;` `stderr.write-via-stream: func(data: stream<u8>) -> future<result<_, error-code>>;`. Note these three are *not* `async func`; they return immediately and the I/O happens through the stream/future. — [stdio.wit @ v0.3.0](https://github.com/WebAssembly/WASI/blob/v0.3.0/proposals/cli/wit/stdio.wit)
- `wasi:cli/imports@0.3.0` world includes `wasi:clocks/imports`, `wasi:filesystem/imports`, `wasi:sockets/imports`, `wasi:random/imports` and imports `environment`, `exit`, `stdin`, `stdout`, `stderr`, `terminal-input`, `terminal-output`, `terminal-stdin`, `terminal-stdout`, `terminal-stderr`. — [imports.wit @ v0.3.0](https://github.com/WebAssembly/WASI/blob/v0.3.0/proposals/cli/wit/imports.wit)
- `interface exit { exit: func(status: result); exit-with-code: func(status-code: u8); }`; `interface environment { get-environment: func() -> list<tuple<string, string>>; get-arguments: func() -> list<string>; get-initial-cwd: func() -> option<string>; }`. — [exit.wit](https://github.com/WebAssembly/WASI/blob/v0.3.0/proposals/cli/wit/exit.wit); [environment.wit](https://github.com/WebAssembly/WASI/blob/v0.3.0/proposals/cli/wit/environment.wit)
- Per-interface changes summarised by wasi.dev: http resources consolidated into `request`/`response`, handler and client are `async func`; sockets consolidated into `types` + `ip-name-lookup`, `listen` returns a stream of sockets; filesystem descriptor methods nearly all async, adds `other(option<string>)` error; clocks `wall-clock` → `system-clock`, `datetime` → `instant` (seconds `u64` → `s64`); random `len` → `max-len` and callers should loop because fewer bytes may be returned. — [wasi.dev/releases/wasi-p3](https://wasi.dev/releases/wasi-p3)
- `wasi:http` handler and worlds: `handle: async func(request: request) -> result<response, error-code>;` `world service { import client; export handler; }` `world middleware { include service; import handler; }`. — [bytecodealliance.org/articles/WASI-0.3](https://bytecodealliance.org/articles/WASI-0.3)
- The Component Model spec itself says: "traditional C programs with a `main()` and calls to `read()`, `write()` and `select()` can run without change in the [WASI] 0.3 `wasi:cli/command` world, which exports `run: async func() -> result`." — [CM-Conc "Summary"](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#summary)

### Inferences
- A TinyWhale "print" primitive maps onto: create `stream<u8>`, call `wasi:cli/stdout.write-via-stream` once (ideally once per program, keeping the writable end open), `stream.write` bytes, and at exit drop the writable end and read the completion future.
- Because `write-via-stream` takes ownership of a readable stream end per call, a language runtime should hold one long-lived stdout stream rather than create one per print (behaviour of calling `write-via-stream` multiple times concurrently was not checked).

### Gaps
- The wasi.dev page says `wasi:cli` "adds a shared `types` interface"; in the v0.3.0 tree the `types` interface is defined inside `stdio.wit` (there is no `types.wit`). Semantics docs (`///` comments) of each function were stripped when reading and not reviewed.
- WIT for filesystem/sockets/http/clocks/random was not read file-by-file; the summary relies on wasi.dev.
- Two descriptions of which http world replaces `proxy` conflict: wasi.dev says `service` replaces `proxy`; the Bytecode Alliance article extraction says `middleware` "replaces the 0.2-era `proxy` world". Wasmtime's `serve` falls back from p3 `Service` to p2 `Proxy`, consistent with `service` being the analogue. — [wasi.dev](https://wasi.dev/releases/wasi-p3) vs [BA article](https://bytecodealliance.org/articles/WASI-0.3); [serve.rs](https://github.com/bytecodealliance/wasmtime/blob/main/src/commands/serve.rs)

## 3. Component Model async at the ABI level (what the spec defines; stable vs gated)

### Takeaway
The 0.3.0-stable (🔀) surface is: the `async` function-type effect, `stream<T>`/`future<T>` types, the `async` + `callback` canonical options (stackless lift) and async lower, and the built-ins `context.get/set`, `backpressure.inc/dec`, `task.return`, `task.cancel`, `waitable-set.{new,wait,poll,drop}`, `waitable.join`, `subtask.{cancel,drop}`, `{stream,future}.{new,read,write,cancel-read,cancel-write,drop-readable,drop-writable}` and `thread.yield`. Still gated/off by default: stackful async lift (🚟), sync variants of stream/future read/write and async cancel variants (🚝), all other `thread.*` built-ins i.e. cooperative threads (🧵), `error-context` (📝), `stream.forward`/`future.forward` (➡️), fixed-length lists (🔧), shared-everything threads (🧵②). Critically for a simple compiler: an `async`-typed export may be lifted with the plain *sync* ABI and may then block.

### Cited Findings

**Where the spec lives**
- There is no `Async.md` on `main` any more (HTTP 404); the document is `design/mvp/Concurrency.md` ("Concurrency Explainer"), and canonical built-ins/grammar are in `design/mvp/Text.md` (the README calls it "text format"), with semantics in `CanonicalABI.md`. — [CM-README](https://github.com/WebAssembly/component-model/blob/main/README.md); [CM-Conc](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md)

**Stable vs gated (verbatim list)**
- Shipped, "not open to breaking changes before the final 1.0 release": "🔀: native concurrency support with `async`, `stream` and `future`", "🗺️: the `map` type", "🏷️: `implements` and `external-id` annotations for imports/exports". — [CM-Text Gated Features](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Text.md#gated-features)
- "All other features are in various stages of implementation, are not enabled by default, may have breaking changes, and, after a suitable [WASI] SG vote, may be shipped as part of a future WASI Developer Preview release": 🪙 value imports/exports and component-level start function; 🪺 nested namespaces; "🚝: enabling more canonical ABI options on more async-related builtins"; "🚟: using `async` with `canon lift` without `callback` (stackful lift)"; "🧵: threading built-ins" (🧵② shared-everything-threads-based); 🔧 fixed-length lists; "📝: the `error-context` type"; 🔗 canonical interface names; 🐘 memory64; 📡 getters and setters; "➡️: `stream.forward` and `future.forward` built-ins". — [CM-Text Gated Features](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Text.md#gated-features)
- "Subsequent WASI Developer Preview releases will include other emoji-[gated features] such as cooperative threads (🧵)." — [CM-README](https://github.com/WebAssembly/component-model/blob/main/README.md)

**The `async` effect and the four lift/lower combinations**
- `async` on a function type means "the function may block before returning its value"; "When a function type does *not* contain `async`, the Component Model traps if the callee blocks at runtime before returning a value". — [CM-Conc Summary](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#summary)
- "Because `async` function exports may be implemented with the *sync* ABI and then call `async` function imports using the *sync* ABI, traditional sync code can compile directly to components exporting `async` functions without having to be rewritten to use source-language concurrency mechanisms". — [CM-Conc Summary](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#summary)
- Lift table (function type / lift option → validity): sync/sync valid (callee blocking → switch to another ready thread in the instance, trap if none); sync/async invalid; async/sync valid (control returns to caller; holds the instance's exclusive lock while running or blocked); async/async+callback valid (lock held only while on the stack, released when returned to the event loop); async/async stackful valid, no lock. Lower table: sync callee/sync lower valid; sync callee/async lower invalid; async callee/sync lower valid ("Caller blocks itself"); async callee/async lower valid (caller resumes and can await the subtask via a waitable set). — [CM-Conc Summary tables](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#summary)
- Canonical options grammar: `canonopt ::= string-encoding=utf8 | string-encoding=utf16 | string-encoding=latin1+utf16 | (memory ...) | (realloc ...) | (post-return ...) | async 🔀 | (callback ...) 🔀`. "The `async` option may only be used with `async` function types". `post-return` "may only be present in `canon lift` when `async` is not present". — [CM-Text Canonical ABI](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Text.md#canonical-abi)
- Validation: "🔀,not(🚟) `async` - `callback` must also be present. Note that with the 🚟 feature (the "stackful" ABI), this restriction is lifted." and "`callback` - the function has type `(func (param i32 i32 i32) (result i32))` and cannot be present without `async` and is only allowed with `canon lift`". — [CM-CABI canonopt validation](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md#canonopt-validation)
- `realloc` type: `(func (param $originalPtr) (param $originalSize) (param $alignment) (param $newSize) (result ptr))`; `memory` is required whenever the ABI must load/store; default string encoding is utf8. — [CM-Text Canonical ABI](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Text.md#canonical-abi)

**Async import (lower) ABI**
- "Async-lowered functions have a maximum of 4 flat parameters (not 16)."; "Async-lowered functions always return their value via linear memory pointer."; "Async-lowered functions always have a single `i32` "status" code." Constants: `MAX_FLAT_PARAMS = 16`, `MAX_FLAT_ASYNC_PARAMS = 4`, `MAX_FLAT_RESULTS = 1`. — [CM-Conc Async Import ABI](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#async-import-abi); [CM-CABI](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md)
- Status code: low 4 bits `0` = not started (STARTING; in-ptr unread, out-ptr unwritten; high 28 bits = new subtask index), `1` = STARTED (in-ptr read, out-ptr unwritten; high bits = subtask index), `2` = RETURNED (done; high bits 0). The caller must keep parameter/result memory alive until the corresponding event arrives. — [CM-Conc Async Import ABI](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#async-import-abi)
- Examples: `async func()` → `(func (result i32))`; `async func() -> string` → `(func (param $out-ptr i32) (result i32))`; `async func(x: f32) -> f32` → `(func (param $x f32) (param $out-ptr i32) (result i32))`. — [CM-Conc Async Import ABI](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#async-import-abi)
- "In *both* the sync and async ABIs, a `future` or `stream` in the WIT-level type translates to a single `i32` in the ABI. This `i32` is an index into the current component instance's handle table." — [CM-Conc Async Import ABI](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#async-import-abi)

**Async export (lift) ABI**
- Sync lift of `export foo: async func(s: string) -> string` is the ordinary 0.2 signature `(func (param $s-ptr i32) (param $s-len i32) (result $retp i32))`. — [CM-Conc Async Export ABI](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#async-export-abi)
- Stackless (callback) lift: `(func (param $s-ptr i32) (param $s-len i32) (result i32))`; value is returned by calling imported `task.return`; result i32 low 4 bits: `0` EXIT (completed and called `task.return`), `1` YIELD, `2` WAIT on the waitable set whose index is in the high 28 bits; companion callback `(func (param i32 i32 i32) (result i32))` is called repeatedly with (event, p1, p2) "until a value of `0` is returned". `CallbackCode`: EXIT=0, YIELD=1, WAIT=2. — [CM-Conc Stackless Async Exports](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#stackless-async-exports); [CM-CABI](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md)
- Stackful lift: "The stackful ABI is currently gated by the 🚟 feature."; signature has no result and the callee calls `task.return`. — [CM-Conc Stackful Async Exports](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#stackful-async-exports)
- "`callback` [is] just an optimization to avoid allocating stacks for async languages that have avoided the need for stackful coroutines by design (e.g., `async`/`await` in JS, Python, C# and Rust)." — [CM-CABI canon lift](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md#canon-lift)
- `task.return`: `(canon task.return (result <valtype>)? <canonopt>* (core func))`, ABI `[lower(FuncT.results)*] -> []`. "When the last thread of a task returns, there is a trap if `task.return` has not been called." "Calling `task.return` when not in the "started" state traps." `canon_task_return` contains `trap_if(not task.opts.async_)` — i.e. `task.return` (and `task.cancel`) cannot be called from a sync-lifted export. — [CM-Conc Returning](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#returning); [CM-CABI canon task.return](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md#-canon-taskreturn)
- A task may keep running after `task.return` (e.g. to keep writing to a stream it returned). — [CM-Conc Returning](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#returning)

**Blocking points**
- Ways to block: sync call of an `async` function that blocks or hits backpressure; `thread.suspend*`; `thread.yield*` or callback `YIELD`; `waitable-set.wait` or callback `WAIT`; "synchronously waiting for a stream or future operation to complete via the `{stream,future}.{,cancel-}{read,write}` built-ins"; sync `subtask.cancel`. If the function type is not `async` and the task has not returned, blocking traps (after trying other ready threads). — [CM-Conc Blocking](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#blocking)

**Waitables**
- Built-ins and ABI signatures: `waitable-set.new: [] -> [i32]`; `waitable-set.wait` / `.poll` (take a `memory` immediate): `[s:i32 payload-addr] -> [event-code:i32]`, payload = "two contiguous `i32`s at the 4-byte-aligned address `payload-addr`"; `waitable-set.drop: [s:i32] -> []`; `waitable.join: [w:i32, maybe_set:i32] -> []`. — [CM-Text Concurrency built-ins](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Text.md#-concurrency-built-ins)
- `EventCode`: NONE=0, SUBTASK=1, STREAM_READ=2, STREAM_WRITE=3, FUTURE_READ=4, FUTURE_WRITE=5, TASK_CANCELLED=6. Subtask states: STARTING=0, STARTED=1, RETURNED=2, CANCELLED_BEFORE_STARTED=3, CANCELLED_BEFORE_RETURNED=4. `task-cancelled` "is never returned by `waitable-set.wait` or `waitable-set.poll`; it may only be delivered as an event code to an `async` `callback` function". — [CM-CABI](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md); [CM-Text waitable-set.wait](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Text.md#-waitable-setwait)
- Wasmtime 41 notes: "The `POLL` callback code has been removed from the canonical ABI for async functions and the `waitable-set.poll` function no longer yields." (so older tutorials listing a POLL callback code are stale). — [WT-REL-41](https://github.com/bytecodealliance/wasmtime/blob/release-41.0.0/RELEASES.md)

**Streams and futures**
- Semantics: "unidirectional unbuffered channels"; a `future`/`stream` in a signature "always refers to the transfer of unique ownership of the *readable end*"; to get a writable end a component calls `{stream,future}.new` and passes the readable end elsewhere. — [CM-Conc Summary](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#summary)
- `stream.new` / `future.new`: `(canon stream.new <typeidx> (core func))`, ABI `[] -> [i64]`; "The first element (in the low 32 bits) is the readable end ... and the second element (in the high 32 bits) is the writable end." — [CM-CABI canon {stream,future}.new](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md#-canon-streamfuturenew)
- `stream.read`/`stream.write`: `[stream-end:i32 ptr num] -> [packed]`; return all-ones (`BLOCKED = 0xffff_ffff`) means the op blocked and an event will follow; otherwise `result` in low 4 bits (COMPLETED=0, DROPPED=1, CANCELLED=2) and `progress` (element count) in the high bits. After `dropped`, "any subsequent operation on the stream other than `stream.drop-{readable,writable}` traps." — [CM-Text stream.read/write](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Text.md#-streamread-and-streamwrite); [CM-CABI](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md)
- `future.read`/`future.write`: `[end:i32 ptr] -> [i32]`; `future-read-result` = completed | cancelled; `future-write-result` = completed | dropped | cancelled. — [CM-Text future.read/write](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Text.md#-futureread-and-futurewrite)
- Gate on sync variants: for `{stream,future}.{read,write}`, "🚝 - `async` is allowed to be omitted, otherwise it must be present". For `{stream,future}.cancel-{read,write}` and `subtask.cancel`: "🚝 - `async` is allowed (otherwise it must be absent)". So in stable 0.3.0, read/write are always the non-blocking (`async`) form returning BLOCKED, and cancels are always synchronous. — [CM-CABI canon {stream,future}.{read,write}](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md#-canon-streamfuturereadwrite)
- Drops: `{stream,future}.drop-{readable,writable}: [end:i32] -> []`. — [CM-Text](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Text.md)
- Type restrictions: `stream T`/`future T` rejected when `T` transitively contains a `borrow`; "`(stream char)` is temporarily rejected". `T` is optional (unit streams/futures are allowed and useful for timing). — [CM-Text Asynchronous value types](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Text.md#asynchronous-value-types)
- TODO list includes "remove the temporary trap ... that occurs when a `read` and `write` of a stream/future happen from within the same component instance". Wasmtime 41: "Intra-component stream/future reads/writes are now allowed for simple data types." — [CM-Conc TODO](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#todo); [WT-REL-41](https://github.com/bytecodealliance/wasmtime/blob/release-41.0.0/RELEASES.md)
- "When function types contain the `async` effect, the return value is returned asynchronously if the call blocks ... and thus there is no need to *additionally* return a `future<T>` value unless *additional* asynchronous signalling is required." — [CM-Text Asynchronous value types](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Text.md#asynchronous-value-types)

**Context (TLS), backpressure, cancellation, yield, threads, error-context**
- `context.get`/`context.set`: `(canon context.get <core:valtype> <u32> (core func))`; "The thread-local storage array's length is currently fixed to contain exactly 2 elements"; intended for the shadow-stack pointer and a TLS struct pointer; immediates `i32` or `i64`, all uses in one component must use the same type; each export call logically gets a fresh thread, so slots are not reused between export calls. — [CM-Conc Thread-Local Storage](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#thread-local-storage)
- Backpressure: `backpressure.inc`/`backpressure.dec` (`[] -> []`) adjust a per-instance counter; while > 0 new export calls stay in "starting". Implicit backpressure: "when an `async`-typed export is lifted with the sync ABI or the stackless async ABI, a component-instance-wide lock is implicitly acquired every time core wasm is executed." Non-`async` functions ignore backpressure and can "barge in". — [CM-Conc Backpressure](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#backpressure)
- Component Invariant 2: "When components implement `async` functions using the 0.3.0 sync or async-callback ABIs, core wasm execution is "run to completion" within the scope of a single component instance". — [CM-Text Component Invariants](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Text.md#component-invariants)
- Cancellation is cooperative: caller calls `subtask.cancel`; callee confirms with `task.cancel` or may still `task.return`; three terminal subtask states. "Currently, only threads that use the `callback` ABI and have returned to their event loop are cancellable ... Until then, `waitable-set.wait` will never return "task cancelled"." — [CM-Conc Cancellation](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#cancellation)
- Spec churn after 0.3.0 visible in Wasmtime 50 (2026-10-20): "Component-model-async has been updated to the latest specification: the `cancellable` immediate has been removed from intrinsics, `subtask.cancel` semantics have been refined, `task.cancel` now traps before the cancel event is delivered, and use of stream/future handles after the other end has been dropped now traps." — [WT-REL-50](https://github.com/bytecodealliance/wasmtime/blob/release-50.0.0/RELEASES.md)
- `thread.yield` is the only `thread.*` built-in in the stable 🔀 set (`[] -> [i32]`); `thread.index`, `thread.new-indirect`, `thread.resume-later`, `thread.suspend`, `thread.{suspend,yield}-then-{resume,promote}` are 🧵; `thread.spawn-ref`, `thread.spawn-indirect`, `thread.available-parallelism` are 🧵②. — [CM-Text Canonical Built-ins grammar](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Text.md#canonical-built-ins)
- Cooperative threads: "currently all threads must execute cooperatively in a sequentially-interleaved fashion, switching between threads only at explicit program points just like ... a traditional OS fiber". — [CM-Conc Summary](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#summary)
- `error-context` type and `error-context.{new,debug-message,drop}` are 📝-gated (not part of 0.3.0). Wasmtime lists error-context as off-by-default, not finished, "sliced out of the original async proposal". — [CM-Text](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Text.md#gated-features); [WT-STAB](https://github.com/bytecodealliance/wasmtime/blob/main/docs/stability-wasm-proposals.md)
- Start functions are sync-typed `func()` and "may not block before returning"; an `async` effect on component instantiation is a post-0.3.0 TODO. — [CM-Conc Interaction with the start function](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#interaction-with-the-start-function)

### Inferences
- The WASI 0.3 WIT (stdout etc.) uses `result<_, error-code>` enums rather than `error-context`, consistent with error-context being ungated; a language should not design around `error-context` yet.
- For a language without its own coroutine transform, the lowest-effort conforming strategy is "sync lift of async exports + async-lowered stream ops + `waitable-set.wait`", which the spec explicitly allows; the callback ABI is the stable route to real intra-component concurrency; stackful lift and cooperative threads are not stable.
- Because a sync-lifted async export holds the instance lock while blocked, a TinyWhale component built this way handles one export call at a time (fine for a CLI `run`, limiting for an HTTP `handle`).

### Gaps
- Binary-format opcodes for the canonical built-ins (`Binary.md`) were not read; a hand-written binary emitter needs them (or can emit WAT and use `wasm-tools`).
- The exact wording of the "temporary trap" for same-instance stream read/write in the Streams section was not read (only the TODO reference and Wasmtime's partial relaxation).
- I did not read `CanonicalABI.md` end-to-end; ordering rules such as "must a waitable be joined to a set before/after the blocked op" were not verified.

## 4. Minimum a hand-written backend must emit ("hello world" CLI writing to stdout; one async export); official minimal examples

### Takeaway
There is no official minimal WASI 0.3 "hello world" in WAT that I could find; the only official WAT examples are the generic stackful/stackless `summarize` examples in `Concurrency.md` and the `.wast` tests in the component-model and Wasmtime repos. The required pieces can be derived from the spec: a component with a memory, the `wasi:cli/run@0.3.0` export (sync-lifted or `async`+`callback`), a lowered `wasi:cli/stdout@0.3.0.write-via-stream`, and the stream/future/waitable-set built-ins.

### Cited Findings
- Official stackless example (complete component in WAT: `canon lower $fetch async (memory $mem) (realloc $realloc)`, `canon waitable-set.new`, `canon waitable.join`, `canon task.return (result string) (memory $mem)`, and `canon lift (core func $main "summarize") async (callback (core func $main "cb")) (memory $mem) (realloc $realloc) (func $summarize async (param "urls" (list string)) (result string))`). The export returns `(WAIT | ($wsi << 4))` i.e. `2 | (set << 4)`; the callback returns the same or calls `task.return` then returns `0` (EXIT). — [CM-Conc Stackless ABI example](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#stackless-abi-example)
- The stackful example in the same document "requires 🚟 for the stackful abi". — [CM-Conc Stackful ABI example](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#stackful-abi-example)
- Async `.wast` tests exist in the spec repo (`test/async/`, e.g. `empty-wait.wast`) and in Wasmtime (`tests/misc_testsuite/component-model/async/`, e.g. `task-builtins.wast`) — usable as machine-checked WAT references. — [component-model test/async/empty-wait.wast](https://github.com/WebAssembly/component-model/blob/main/test/async/empty-wait.wast); [wasmtime async tests](https://github.com/bytecodealliance/wasmtime/blob/main/tests/misc_testsuite/component-model/async/task-builtins.wast)

- Rust's `wasm32-wasip3` ABI note: "The linear memory shadow stack pointer is stored in a component model task context slot instead of a WebAssembly `global`". — [rustc wasm32-wasip3 platform doc](https://doc.rust-lang.org/nightly/rustc/platform-support/wasm32-wasip3.html)

### Inferences (derived from the cited ABI rules; NOT taken from an official example and NOT executed — validate with `wasm-tools validate` and Wasmtime ≥ 46 before relying on it)
Minimum for hello-world, simplest variant (sync-lifted `run`):
1. Core module with an exported linear memory containing the message bytes. `realloc` is only required if some lifted/lowered type needs allocation (none of the functions below pass strings/lists by value, so it may be omittable; unverified).
2. Component-level imports: instance `wasi:cli/stdout@0.3.0` (func `write-via-stream`, plus the `error-code` type from `wasi:cli/types@0.3.0`); component-level export: instance `wasi:cli/run@0.3.0` with `run`.
3. Canonical definitions: `canon lower` of `write-via-stream` (sync; core type `(func (param i32) (result i32))`: stream readable-end handle in, future handle out); `canon stream.new` for `stream<u8>` (`[] -> [i64]`, low 32 = readable, high 32 = writable); `canon stream.write` for `stream<u8>` with `async` and `(memory …)`; `canon stream.drop-writable`; `canon future.read` for `future<result<_, error-code>>` with `async` and `(memory …)`; `canon future.drop-readable`; `canon waitable-set.new`, `canon waitable.join`, `canon waitable-set.wait (memory …)`, `canon waitable-set.drop`.
4. `run` body: `stream.new` → call `write-via-stream(readable)` → `stream.write(writable, ptr, len)`; if result is `0xffff_ffff` (BLOCKED), `waitable.join(writable, set)` and `waitable-set.wait(set, payload_ptr)` until a STREAM_WRITE (3) event; loop until all bytes are reported in `progress`; `stream.drop-writable`; `future.read(future, buf)`, wait for FUTURE_READ (4) if BLOCKED; `future.drop-readable`; return `i32` 0 (`ok`) — the sync-lifted core signature of `run: async func() -> result` being `(func (result i32))`.
5. `canon lift` of the core `run` *without* `async` (sync ABI is valid for an `async` function type and is allowed to block), typed as `(func async (result (result)))` at the component level.

Minimum for one genuinely async export (stable ABI): same as above but lift with `async (callback $cb)`; core export has `(result i32)` returning EXIT/YIELD/WAIT codes; export a callback `(func (param i32 i32 i32) (result i32))`; return the value via `canon task.return (result …)`; never call `waitable-set.wait` inside (return `WAIT | set<<4` instead); keep per-task state reachable via `context.get/set` slot(s) since the stack is not preserved between callback invocations.

- A compiler that does not want to produce the component binary encoding itself can emit a core module using the wit-component naming convention plus an embedded WIT world and run `wasm-tools component new`; the precise import *module* names (e.g. `$root`, `[export]$root`, interface names) were not verified here.

### Gaps
- No official "hello world to stdout on WASI 0.3" in WAT was found on wasi.dev, the Component Model book, or the spec repo; the Component Model book's table of contents has no WAT-level or async pages (only per-language guides and a "Migrating from WASI 0.2 to WASI 0.3" page).
- Whether a waitable must already be in a set at the time the blocked op is started, and exact trap conditions around `waitable.join` on a writable end with a pending op, were not verified.
- Binaryen's support for emitting components is not covered here (Binaryen emits core modules; component wrapping would need `wasm-tools` or a custom encoder) — outside this topic's sources.

## 6. Compatibility: mixing 0.2 and 0.3, adapters, other runtimes

### Takeaway
0.2 components keep running on 0.3-capable hosts (Wasmtime implements both side by side and dispatches per component); primary sources describe host-side polyfilling of 0.2 on top of 0.3 but I found no primary statement about a guest-side 0.2↔0.3 adapter component or about one component importing both versions. Besides Wasmtime, jco is the only other runtime named by primary sources, with its 0.3 support described inconsistently (full vs experimental).

### Cited Findings
- "Implementations may keep supporting WASI 0.2 alongside 0.3, either by implementing both or by virtualizing 0.2 on top of 0.3." (tool-extracted wording) — [wasi.dev roadmap](https://wasi.dev/roadmap)
- Migration is not required to run on a 0.3-capable runtime; `wasmtime serve` runs both. — [wasi.dev/releases/wasi-p3](https://wasi.dev/releases/wasi-p3)
- Wasmtime CLI links p2 and p3 host implementations into the same linker and picks the entrypoint by which export exists (p3 `Command`/`Service` first, else p2). — [run.rs](https://github.com/bytecodealliance/wasmtime/blob/main/src/commands/run.rs); [serve.rs](https://github.com/bytecodealliance/wasmtime/blob/main/src/commands/serve.rs)
- Spec-level interop: "The new async ABI can be used alongside or instead of the existing [WASI] 0.2 "sync ABI"" and "both sync-ABI-calls-async-ABI and async-ABI-calls-sync-ABI pairings have well-defined, composable behavior for both inter-component and intra-component calls." — [CM-Conc Summary](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#summary)
- Long-term: "P1 modules still work. P2 components still work." and "existing P3 components will still be supported with the help of tools and adapters." — [The Road to Component Model 1.0](https://bytecodealliance.org/articles/the-road-to-component-model-1-0)
- jco: launch article says jco "also supports all of WASI 0.3" and "A release that has support enabled by default will be going out soon." (Jun 11, 2026); wasi.dev lists jco as a 0.3 runtime; migration guide lists jco "latest" with 0.3 host bindings in the `preview3-shim` package. A search summary reports wasi.dev's languages page labels jco's 0.3 support "experimental" (not opened directly — unverified). — [BA article](https://bytecodealliance.org/articles/WASI-0.3); [wasi.dev/releases/wasi-p3](https://wasi.dev/releases/wasi-p3); [migration guide](https://component-model.bytecodealliance.org/design/migrating-to-p3.html)

- Nothing in the Component Model forbids a component from importing both `wasi:…@0.2.x` and `wasi:…@0.3.x` interfaces (they are distinct versioned names), and Wasmtime's CLI adds both to one linker, so mixing likely works on Wasmtime; this is not confirmed by a primary statement or test.

## 7. What is planned next that affects a language design decision made now

### Takeaway
Near-term 0.3.x releases are expected to add cooperative threads (🧵) and stream splicing/forwarding, with stackful async lift and extended async built-in options also in the queue; a "lazy ABI" (lazy value lowering, multivalue returns, error context in result error cases) is planned as an opt-in 0.3.x option that becomes the default at Component Model 1.0, with adapters for older components. The 🔀 surface is frozen against breaking changes, so targeting async/stream/future with the sync or callback ABI today is safe; designing around `error-context`, stackful lift or threads is not yet.

### Cited Findings
- "Cooperative threads support will ship in a follow-up WASI P3 minor release." It will "pave the road for shared-everything threads later." Stream splicing will also ship in an early P3 follow-up release. — [The Road to Component Model 1.0](https://bytecodealliance.org/articles/the-road-to-component-model-1-0)
- "the lazy ABI ships as a new opt-in option in a 0.3.x minor release"; at 1.0 it becomes the default with an adapter converting eager components; bundled with multivalue returns and an error context in each result's error case; a GC-memory ABI option is at pre-proposal stage; implementers targeting 1.0 without P3 will not need the current `cabi_realloc` calling convention; "the recursion check was removed during P3 development." (tool-extracted; partially paraphrased) — [The Road to Component Model 1.0](https://bytecodealliance.org/articles/the-road-to-component-model-1-0)
- 1.0 spec will include only "the good parts" of the P3 spec. — [The Road to Component Model 1.0](https://bytecodealliance.org/articles/the-road-to-component-model-1-0)
- Roadmap lists "threading built-ins" among candidate Component Model features still gated and needing a Subgroup vote. — [wasi.dev roadmap](https://wasi.dev/roadmap)
- Rust doc (dated statement): "As of 2026-09-03 cooperative multithreading is not yet supported on this target in Rust"; component model work "is expected to be complete before the end of the year"; "it is currently intended that by the end of 2026 this support will all be enabled by default". — [rustc wasm32-wasip3 platform doc](https://doc.rust-lang.org/nightly/rustc/platform-support/wasm32-wasip3.html)
- Spec TODO list (concurrency): cancellation notification for stackful ABI; `stream<char>`; instance-lifetime built-ins; `async` effect on component instantiation and on resource destructors; JSPI-like suspension of a child's sync calls; `strict-callback` option; first-class function closures; pipelining of `stream.read`/`write`; promise pipelining; integration with `shared`. — [CM-Conc TODO](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#todo)
- "Until the Core WebAssembly [shared-everything-threads] proposal allows Core WebAssembly function types to be annotated with `shared`, `thread.new-indirect` can only call non-`shared` functions ... and thus currently all threads must execute cooperatively"; cooperative threads "do not allow a single component instance to increase its internal parallelism". — [CM-Conc Summary](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#summary)
- Buffers for stream/future copies are "Core WebAssembly linear (or, soon, GC) memory". — [CM-Conc Summary](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#summary)
- Current restrictions a language's type mapping must respect: no `borrow` inside `stream`/`future` element types; `stream<char>` rejected; start functions cannot block. — [CM-Text Asynchronous value types](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Text.md#asynchronous-value-types); [CM-Conc](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#interaction-with-the-start-function)

### Inferences
- Safe-to-build-on today (frozen, on by default in Wasmtime ≥ 46): `async func`, `stream<T>`, `future<T>`, sync lift of async exports, async+callback lift, async lower, waitable sets, `task.return`, `context.get/set` (2 slots), backpressure, `thread.yield`.
- Risky to bake into language semantics now: `error-context` (gated, unfinished in Wasmtime), stackful lift (gated; cancellation story unfinished), `thread.*` green threads (gated; possibly stable in a 0.3.x within months but undated), `stream.forward` (gated), sync stream ops (🚝).
- A language-level design that expresses concurrency as tasks/futures/streams and keeps the lowering strategy (sync-blocking vs callback state machine vs future stackful/threads) an internal compiler choice is aligned with the spec's stated intent that these are encapsulated implementation details of a component.
- The lazy ABI means the linear-memory `realloc`-based convention is not the final ABI; keeping the ABI glue isolated in the backend will reduce future churn.

### Gaps
- No dated commitment for which 0.3.x adopts cooperative threads, stackful lift, 🚝 options or the lazy ABI.
- "The Road to Component Model 1.0" was read via a summarising tool; the lazy-ABI details should be re-checked against the article before being quoted.
- No primary information on browser-engine implementation progress (the 1.0 gating factor).
