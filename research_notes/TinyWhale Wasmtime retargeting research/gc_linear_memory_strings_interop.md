# WasmGC + Component Model / WASI 0.3 interop: linear memory mixing, strings as GC arrays (state as of 2026-11-14)

Conventions: every date in "(checked 2026-11-14)" means I read the live primary source on that day. "main" means the default branch of the named repo on 2026-11-14. Wasmtime release dates/notes are from the per-release `RELEASES.md` files and the v47 GitHub release page. Items I could not confirm from a primary source are labelled UNVERIFIED and repeated under Gaps.

## 1. Canonical ABI and GC: is linear memory + `realloc` required, and what is the status of the GC ABI option?

### Takeaway
As of 2026-11-14 the Component Model canonical ABI on `main` is defined only over linear memory; the "GC ABI" is still an open pre-proposal (component-model issue #525) with unresolved design problems as recently as 2026-11-04, and it is not in the spec text or grammar. Wasmtime has a `component-model-gc` flag, but its own docs call the support "_very_ incomplete" and the fused-adapter compiler on `main` still contains 69 `todo!("CM+GC")` sites, so it is not usable for a real language today.

### Cited Findings

Spec (linear-memory ABI):
- The canonical-option grammar on `main` contains only `string-encoding=utf8|utf16|latin1+utf16`, `(memory ...)`, `(realloc ...)`, `(post-return ...)`, `async` (🔀) and `(callback ...)` (🔀). There is no `gc` or `core-type` option (checked 2026-11-14). — [component-model Text.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Text.md)
- `memory` option: "If the Canonical ABI needs to load or store, validation requires this option to be present (there is no default)." `realloc`: "If the Canonical ABI needs `realloc`, validation requires this option to be present (there is no default)." — [component-model Text.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Text.md)
- Exact validation rules (checked 2026-11-14): "`lower(T)` requires `memory` if `T` contains a `list` or `string`"; "`lift(T)` requires `realloc` if `T` contains a `list` or `string`"; "if `realloc` is present then `memory` must be present". For `canon lift` (an export): lift rules apply to params, lower rules to the result; `realloc` is additionally required if flattened params exceed `MAX_FLAT_PARAMS`, `memory` if flattened results exceed the max. For `canon lower` (an import): lower rules apply to params, lift rules to the result; `memory` is required if flattened params or results exceed the flat limits. — [CanonicalABI.md, "canonopt validation", "canon lift", "canon lower"](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md)
- `realloc` has core type `(func (param addr addr addr addr) (result addr))`, i32 addresses (i64 only under the 🐘 memory64 gate). — [CanonicalABI.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md)
- Records/tuples/variants themselves are flattened to core values and need no memory unless the flat limits are exceeded; `list` and `string` always go through memory (rules above). — [CanonicalABI.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md)
- Async streams/futures (WASI 0.3) also use linear memory: `stream.read`/`stream.write` core functions have type `(func (param i32 T T) (result T))` (handle, pointer, length), and when the stream has an element type "`memory` is required to be present". `canon_stream_write(stream_t, opts, i, ptr, length)` lifts from a `ReadableGuestBuffer` at `ptr`. — [CanonicalABI.md, `canon stream.read/write`](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md)
- The spec text explicitly says GC memory is future work: "Currently wasm memory is always 32-bit or 64-bit linear memory, but soon GC memory will be added." and `canon_thread_new_ref` "will be added as part of adding a [GC ABI option] to the Canonical ABI". — [CanonicalABI.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md)
- Explainer: "In the future, a new ABI option will likely be added for [wasm-gc] to replace these integer offsets with typed GC references" (link target is issue #525). — [Explainer.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Explainer.md)
- Explainer also says `realloc` itself is expected to change: "In the next iteration of the Component Model ABI ... the `realloc` ABI option will likely be replaced (in a non-breaking transitional manner) with a combination of caller-supplied buffers and [lazy] value copying." — [Explainer.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Explainer.md)
- The gated-features legend on `main` lists 🔀 (async/stream/future), 🗺️, 🏷️ as shipped in a WASI preview, and 🪙 🪺 🚝 🚟 🧵 🧵② 🔧 📝 🔗 🐘 📡 ➡️ as not stable. No GC gate is listed. A grep for 🛸 across CanonicalABI.md, Explainer.md, Text.md, Binary.md on `main` returns nothing (checked 2026-11-14). — [Text.md gated features](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Text.md)

GC ABI pre-proposal (#525):
- "Pre-Proposal: Wasm GC Support in the Canonical ABI", opened by Nick Fitzgerald (fitzgen) on 2025-06-03; still open with no milestone on 2026-11-14. Proposes a `gc` canonopt (binary `0x09`) plus a `core-type` canonopt (`0x08 <idx>`) that "must be present if and only if the `gc` option is present". — [component-model #525](https://github.com/WebAssembly/component-model/issues/525)
- Proposed mapping: `string` -> ref to array (`utf8` -> `(array i8)`, `utf16` -> `(array i16)`, `latin1+utf16` unresolved between `(array i8)` and a dynamically typed `(ref array)`); `list<T>` -> ref to array of T's storage type; `record`/`tuple` -> ref to struct; `variant`/`option`/`result` -> ref to an empty supertype struct with one subtype per case in a `rec` group; `enum`/`flags` -> `i32`; `own`/`borrow`/`future`/`stream`/`error-context` -> `externref`. — [component-model #525](https://github.com/WebAssembly/component-model/issues/525)
- Open issues in that thread: trap-on-drop of `externref` handles for own/borrow/stream/future (2025-06, explicit drops first, finalizers later); interaction with the stackless async ABI and a GC "box" for `task.return` (2026-03); request for finalizers/weakrefs split to issue #752 (2026-10-22); and on 2026-11-04 fitzgen reported that variants with `record`/`tuple` payloads cannot be lowered unambiguously and proposed canonical unique GC representations for CM types (i.e. the type mapping itself is still changing). — [component-model #525](https://github.com/WebAssembly/component-model/issues/525)
- In the same thread (2026-04-22/23) Justin Fagnani and others described the cost of copying through linear memory for GC languages as the motivation to get this done. — [component-model #525](https://github.com/WebAssembly/component-model/issues/525)
- Lazy value lowering (#383, Luke Wagner, opened 2024-07-25, open, labelled `pre-1.0`) is the related redesign that removes the adapter-driven `realloc` call; last activity is a 2026-05-19 community proposal for a narrow first slice with no maintainer reply visible. — [component-model #383](https://github.com/WebAssembly/component-model/issues/383)

### Inferences
- A TinyWhale component that passes any `string`, `list<T>`, or `stream<T>` across the boundary must, today, export a linear memory; it must also export a `realloc` whenever a string/list flows host -> guest (import results, export params) or export params exceed the flat limit. A guest that only sends bytes out (e.g. writes to a `stream<u8>`) needs `memory` but, by the validation rules, not `realloc`.
- Pure scalar/record interfaces (flattened values within the flat limits) need neither memory nor realloc, so a "constrained locals/multi-value" host ABI works only until the first string/list.
- The GC ABI should be treated as not available for the whole planning horizon of a restart: the spec mapping changed in the last two weeks, async handle semantics are unresolved, and Wasmtime panics (`todo!`) on the paths that matter.
- Because #525 maps `string` (utf8) to `(array i8)` and `list<u8>` to `(array i8)`, choosing `(array i8)` UTF-8 internally is the representation most likely to become zero-copy if/when the GC ABI lands. This is a forward-compatibility guess, not a guarantee, since the mapping is still in flux.

- Whether `-W component-model-gc` works for any type at all (e.g. scalars only) was not tested.

## 2. If the GC ABI is not usable: the standard pattern for a GC language to call WASI today

### Takeaway
Every GC-language toolchain I could verify uses the same pattern: a WasmGC core module that also defines a small linear memory plus `cabi_realloc`, wrapped with `wasm-tools component embed/new`, copying data element-by-element between GC arrays and that memory at each boundary crossing. There is no core instruction that bulk-copies between a GC array and linear memory; two proposals address parts of this (More Array Constructors at phase 1, Multibyte Array Access at phase 2), neither standardized.

### Cited Findings
- Chris Fallin (Wasmtime), 2025-05-21: "The two coexist just fine." WIT imports pass data through the canonical ABI in linear memory allocated with `cabi_realloc`; a module can have both linear memory and GC allocations, so a toolchain can generate code using both; reusing the standard component tooling on a GC module should work in principle. — [BA Zulip, "Wasm GC and Preview 2"](https://bytecodealliance.github.io/zulip-archive/stream/217126-wasmtime/topic/Wasm.20GC.20and.20Preview.202.html)
- Worked example of exactly this on Wasmtime: scala-wasm (Scala.js fork) compiles WasmGC code that exports `wasi:cli/run@0.2.0` and imports `wasi:cli/stdout@0.2.0` / `wasi:io/streams@0.2.0`, builds with `wasm-tools component embed ... --encoding utf16`, `wasm-tools component new`, `wac plug`, and runs with `wasmtime -W function-references,gc out.wasm` (article dated 2025-10-28; the flags are no longer needed since Wasmtime 47). — [VirtusLab, "Bringing Scala to server side"](https://virtuslab.com/blog/scala/bringing-scala-to-server-side/)
- WasmGC MVP array instructions: `array.copy` copies only between two arrays; `array.new_data` / `array.init_data` copy from a data segment into an array; there is no instruction with a memory operand. — [WebAssembly/gc MVP.md](https://github.com/WebAssembly/gc/blob/main/proposals/gc/MVP.md)
- "More Array Constructors" (champion Nick Fitzgerald) is at Phase 1 on 2026-11-14 and proposes `array.new_array`, `array.new_memory dst src` ("Create an array of type `dst` from a subslice of the memory `src`") and `array.new_table`. It covers memory -> new array only; it does not add an array -> memory copy. — [WebAssembly/proposals README](https://github.com/WebAssembly/proposals/blob/main/README.md); [more-array-constructors Overview](https://github.com/WebAssembly/more-array-constructors/blob/main/proposals/more-array-constructors/Overview.md)
- "Multibyte Array Access" (champion Brendan Dahl) is at Phase 2 on 2026-11-14: reuses linear-memory load/store instructions on GC numeric arrays (e.g. `i32.load`/`i64.load` on an `(array i8)`), motivated by "sequences of single-element operations that are highly inefficient". — [WebAssembly/proposals README](https://github.com/WebAssembly/proposals/blob/main/README.md); [multibyte-array-access Overview](https://github.com/WebAssembly/multibyte-array-access/blob/main/proposals/multibyte-array-access/Overview.md)
- Multi-memory is a finished proposal (Wasm 3.0) and Tier 1 in Wasmtime; the `memory` canonopt takes an explicit core memory index, so the marshalling memory can be a dedicated memory. — [finished-proposals.md](https://github.com/WebAssembly/proposals/blob/main/finished-proposals.md); [Wasmtime "Wasm Proposals"](https://docs.wasmtime.dev/stability-wasm-proposals.html); [Text.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Text.md)
- The spec assumes `realloc` out-of-memory traps ("will trap (via `unreachable`)"), which simplifies a bump allocator: no failure protocol is needed. — [CanonicalABI.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md)
- `post-return` (sync exports only; cannot be combined with `async`) is the hook where a callee frees/reset memory used for returned strings/lists. — [CanonicalABI.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md); [Explainer.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Explainer.md)
- Zena (new WasmGC language, compiler in TypeScript then self-hosted) states its compiler "synthesizes the required Canonical ABI lifting and lowering adapters directly into the emitted Wasm module" with no bindings generator; its README (2026-11-14) still labels this "Native WIT & Component Model Integration (In Progress)". — [Zena announcement, 2026-09-09](https://justinfagnani.com/2026/09/09/zena-a-new-wasm-first-programming-language/); [elematic/zena README](https://github.com/elematic/zena)
- Kotlin's team (Slava Kuzmich, 2024-04-18) tested WasmGC components by transpiling a stub component with jco and swapping in the real WasmGC core module; in 2024-01 `wasm-tools component new` needed `WasmFeatures::all()` to accept GC+exceptions modules. Historical only. — [BA Zulip, "Wasm Components and WasmGC"](https://bytecodealliance.github.io/zulip-archive/stream/206238-general/topic/Wasm.20Components.20and.20WasmGC.html)

### Inferences
- Copy cost today is a per-element loop (`array.get_u` + `i32.store8`, or `i32.load8_u` + `array.set`), i.e. O(n) with a bounds check per element unless Cranelift hoists it; nothing verified here quantifies it for Wasmtime. Wasmtime-side `array.copy` itself was reported slow by an early adopter in 2026-06 with "a fix ... expected to ship in the next release" ([wasmtime #13216 archive](https://bytecodealliance.github.io/zulip-archive/stream/225357-git-wasmtime/topic/wasmtime.20.2F.20issue.20.2313216.20Enable.20Wasm.20GC.20by.20default.html)).
- Option ranking by complexity for a small compiler: (i) single module, one memory used purely as scratch with a bump allocator reset per call - simplest, one extra copy per crossing; (ii) same but a second dedicated memory via multi-memory - no functional gain unless the language also wants its own memory 0; (iii) a separate adapter module/component written in Rust/C that owns the memory - requires passing GC refs or bytes across a core-module boundary, which cannot be expressed through the linear-memory canonical ABI anyway, so it only works as a core-module link inside one component and adds toolchain weight.
- A bump allocator that resets at call boundaries is unsafe under WASI 0.3 async if buffers must stay valid across suspension (pending `stream.read`/`stream.write`, async export params); buffers handed to in-flight stream operations need a lifetime tied to the operation, not the call. This follows from the stream ABI taking a guest pointer for a possibly-blocked copy, but I did not find a source spelling out the allocator consequence.

### Gaps
- No primary benchmark of GC-array <-> linear-memory copy overhead on Wasmtime was found. A slide deck by tanishiking ("Implementing and Evaluating a High-Level Language with WasmGC and the Wasm Component Model: Scala's case") reportedly mentions "WasmGC <-> Linear Memory copy overhead", but I only saw a search snippet; UNVERIFIED.
- Whether Wasmtime or any engine implements `array.new_memory` or multibyte array access behind a flag: not found.
- Zena's actual lowering code (scratch memory layout, allocator) was not inspected.

## 3. Can one core module freely use both GC types and linear memory in Wasmtime? Restrictions and pitfalls

### Takeaway
Yes. Since Wasmtime 47.0.0 (2026-07-20) GC, typed function references and exception handling are on by default and Tier 1 (Cranelift only), and nothing restricts a module from also defining memories. The real constraints are structural: linear memory cannot hold GC references, GC objects have no interior pointers, and Wasmtime's GC heap is a separate sandboxed region with its own size tunables and a collector tuned for short-lived instances.

### Cited Findings
- "Wasmtime now has the WebAssembly GC proposal enabled by default." and "Wasmtime now has the WebAssembly exception-handling proposal enabled by default." (47.0.0, released 2026-07-20). — [Wasmtime v47.0.0 release](https://github.com/bytecodealliance/wasmtime/releases/tag/v47.0.0)
- `Config::wasm_gc`: "This feature is `true` by default." (docs for main/52.0.0-dev). — [wasmtime config.rs](https://github.com/bytecodealliance/wasmtime/blob/main/crates/wasmtime/src/config.rs); [Config docs](https://docs.wasmtime.dev/api/wasmtime/struct.Config.html)
- `gc`, `function-references`, `exception-handling`, `multi-memory` are Tier 1 in Wasmtime with footnote "Winch does not yet support this proposal at Tier 1." Wasmtime 50.0.0 (2026-10-20): "Winch no longer enables the GC types, exceptions, or tail-call proposals by" default. — [Wasmtime "Wasm Proposals"](https://docs.wasmtime.dev/stability-wasm-proposals.html); [Wasmtime RELEASES.md, release-50.0.0](https://github.com/bytecodealliance/wasmtime/blob/release-50.0.0/RELEASES.md)
- fitzgen, 2026-06-09: Wasm GC "promoted ... to tier 1 stability and enabled it by default on `main`"; tracking issue #13216 closed 2026-06-08. — [BA Zulip archive of wasmtime #13216](https://bytecodealliance.github.io/zulip-archive/stream/225357-git-wasmtime/topic/wasmtime.20.2F.20issue.20.2313216.20Enable.20Wasm.20GC.20by.20default.html)
- GC and components coexist: see Fallin quote in section 2; the scala-wasm example runs a GC core module inside a WASI 0.2 component on Wasmtime. — [BA Zulip](https://bytecodealliance.github.io/zulip-archive/stream/217126-wasmtime/topic/Wasm.20GC.20and.20Preview.202.html); [VirtusLab](https://virtuslab.com/blog/scala/bringing-scala-to-server-side/)
- Wasmtime GC heap design: "A reference to a GC object is not a native pointer, it is a 32-bit index into the GC heap's underlying linear memory"; guard pages replace explicit bounds checks; integrates with the pooling allocator. The GC heap is distinct from the module's own memories. — [Bytecode Alliance, "GC and Exceptions in Wasmtime", 2026-07-20](https://bytecodealliance.org/articles/wasmtime-gc)
- GC heap has separate tunables (added in 45.x: "Wasmtime now supports a separate set of GC tunables different from the main" memory tunables): `gc_heap_reservation` (default 4 GiB on 64-bit, 10 MiB on 32-bit), `gc_heap_guard_size` (32 MiB / 64 KiB), `gc_heap_reservation_for_growth` (2 GiB / 1 MiB), plus CLI `-O gc-heap-initial-size`, `gc-heap-may-move`, `pooling-total-gc-heaps` (default 1000). 50.0.0 added `Store::gc_heap_grow`. — [Config docs](https://docs.wasmtime.dev/api/wasmtime/struct.Config.html); [cli-flags lib.rs](https://github.com/bytecodealliance/wasmtime/blob/main/crates/cli-flags/src/lib.rs); [RELEASES.md release-45.0.0](https://github.com/bytecodealliance/wasmtime/blob/release-45.0.0/RELEASES.md); [RELEASES.md release-50.0.0](https://github.com/bytecodealliance/wasmtime/blob/release-50.0.0/RELEASES.md)
- GC design goal "Independent from linear memory"; interior pointers are a Post-MVP idea ("True inner pointers introduce significant complications to GC ..."; proposed as separate fat "interior references"), so the MVP has none. — [WebAssembly/gc Overview.md](https://github.com/WebAssembly/gc/blob/main/proposals/gc/Overview.md); [WebAssembly/gc Post-MVP.md](https://github.com/WebAssembly/gc/blob/main/proposals/gc/Post-MVP.md)
- Security history relevant to maturity: 48.x/49.x patch releases fixed "Mis-typed WebAssembly tag imports can lead to GC heap corruption" and "Rooting for GC values live across `try_call` may be missing, causing GC heap corruption"; since 46.0.0 heap corruption is surfaced as a `WasmtimeBug` error instead of a panic. — [RELEASES.md release-48.0.0](https://github.com/bytecodealliance/wasmtime/blob/release-48.0.0/RELEASES.md); [RELEASES.md release-46.0.0](https://github.com/bytecodealliance/wasmtime/blob/release-46.0.0/RELEASES.md)
- Scala's team notes that under the current threads proposal WasmGC programs cannot use threads (shared-everything-threads is Phase 1). — [VirtusLab](https://virtuslab.com/blog/scala/bringing-scala-to-server-side/); [WebAssembly/proposals README](https://github.com/WebAssembly/proposals/blob/main/README.md)

### Inferences
- Linear memory stores only bytes, so a GC ref cannot be written into it; a language that needs to hand a GC object to memory-side code must use an index into a `(table anyref)`/`externref` table (a handle table) and manage slot lifetime manually. For TinyWhale, where memory would be scratch-only, this never arises: all long-lived data stays in GC structs/arrays and only bytes/scalars are serialized.
- Component-model resource handles (`own`/`borrow`, stream/future ends) are i32 indices in the linear-memory ABI, so they are stored in GC structs as plain `i32` fields; without finalizers (#752, open) they must be dropped explicitly or by an affine/ownership discipline (Zena uses affine `resource class`; see section 5).
- Two heaps means two limits: an embedder limiting "memory" must also consider the GC heap reservation; the defaults reserve 4 GiB of virtual address space per GC heap on 64-bit.

### Gaps
- No source states a specific performance penalty for a module that mixes GC and linear memory in Wasmtime; none is expected from the design, but this is unmeasured.
- Winch (baseline compiler) cannot run GC code; only Cranelift. Pulley (interpreter) GC status not checked.

## 4. Strings: representations, status, copying to WASI 0.3, literals

### Takeaway
On Wasmtime the only practical choices are toolchain-defined GC arrays: `(array i8)` holding UTF-8 or `(array i16)` holding UTF-16; stringref is Phase 1 with no Wasmtime plans and JS String Builtins are a JS-embedding feature Wasmtime says it will not build in. For WASI 0.3, where stdout takes a `stream<u8>` and the default CM string encoding is UTF-8, an immutable `(array i8)` UTF-8 string needs exactly one byte-copy into scratch memory and no transcoding.

### Cited Findings
- Stringref ("Reference-Typed Strings", champion Andy Wingo) is Phase 1 on 2026-11-14. — [WebAssembly/proposals README](https://github.com/WebAssembly/proposals/blob/main/README.md)
- Wasmtime position (2024-10-20/22): Alex Crichton: "No plans currently" to implement stringref. fitzgen: stringref "was baking the semantics of JS strings into the wasm language"; non-JS toolchains should lower strings to `(array i8)` (UTF-8) or `(array i16)` (UTF-16) and implement semantics themselves; "it is unlikely that Wasmtime will ever have built-in support for these functions" (JS string builtins), though an embedder could define them on a `Linker`. Chris Fallin: "there's no interop with JS on Wasmtime". — [BA Zulip, "stringref implementation in WasmTime"](https://bytecodealliance.github.io/zulip-archive/stream/217126-wasmtime/topic/stringref.20implementation.20in.20WasmTime.html)
- Stringref and JS string builtins do not appear in Wasmtime's proposal status page or CLI feature flags (checked 2026-11-14). — [Wasmtime "Wasm Proposals"](https://docs.wasmtime.dev/stability-wasm-proposals.html); [cli-flags lib.rs](https://github.com/bytecodealliance/wasmtime/blob/main/crates/cli-flags/src/lib.rs)
- JS String Builtins (champion Ryan Hunt) is a finished proposal (WG 2025-07-23, listed under Wasm 3.0) affecting "core, js-api"; it works by importing functions from the JS host. — [finished-proposals.md](https://github.com/WebAssembly/proposals/blob/main/finished-proposals.md)
- Component-model string encodings: `utf8` (default), `utf16`, `latin1+utf16`; chosen per lift/lower by canonopt, transcoded by the adapter when the two sides differ. `store_string` transcoding uses worst-case allocation then a shrinking `realloc`. — [CanonicalABI.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md)
- WASI 0.3 stdio is byte streams: `wasi:cli` 0.3 draft `stdin.read-via-stream: func() -> tuple<stream<u8>, future<result<_, error-code>>>` and stdout "Write the given stream to stdout" (file tagged `@since(version = 0.3.0-rc-2025-09-16)` on `main`, checked 2026-11-14). — [wasi-cli wit-0.3.0-draft/stdio.wit](https://github.com/WebAssembly/wasi-cli/blob/main/wit-0.3.0-draft/stdio.wit)
- Wasmtime 46.0.0 (2026-06-22): "Wasmtime now supports WASI 0.3.0 by default and the `component-model-async` wasm feature is now enabled by default." — [RELEASES.md release-46.0.0](https://github.com/bytecodealliance/wasmtime/blob/release-46.0.0/RELEASES.md)
- String literals with GC arrays: `array.new_data $t $d : [i32 i32] -> [(ref $t)]` allocates from a (passive) data segment given offset and length; `array.init_data` copies a data-segment range into an existing array; `array.new_fixed $t N` takes N operands. Constant expressions may use `struct.new`, `struct.new_default`, `array.new`, `array.new_default`, `array.new_fixed`, `ref.i31`, `global.get` of preceding immutable globals; "`array.new_data` and `array.new_elem` are not for the time being". — [WebAssembly/gc MVP.md](https://github.com/WebAssembly/gc/blob/main/proposals/gc/MVP.md)
- Binaryen's C API exposes the needed nodes: `BinaryenArrayNewData`, `BinaryenArrayNewFixed`, `BinaryenArrayInitData`, `BinaryenArrayCopy`, `BinaryenStructNew`, `BinaryenCallRef`. — [binaryen-c.h](https://github.com/WebAssembly/binaryen/blob/main/src/binaryen-c.h)
- Binaryen has stringref in its IR plus `--string-lifting` / `--string-lowering` passes targeting JS string builtins (imported strings); this pipeline is JS-oriented. — [Binaryen GC Optimization Guidebook](https://github.com/WebAssembly/binaryen/wiki/GC-Optimization-Guidebook); [Binaryen CHANGELOG](https://github.com/WebAssembly/binaryen/blob/main/CHANGELOG.md)
- Prior art choosing `(array i8)`: Guile Hoot uses stringref only as an intermediate form, then "a lowering pass replaces stringref instructions with something resembling the JS string builtins proposal but with 8-bit code units rather than 16-bit and the unfortunate limitation that strings are copied at the Wasm/host boundary". — [Hoot manual, Status](https://files.spritely.institute/docs/guile-hoot/latest/Status.html)
- Prior art choosing UTF-16 at the component boundary: MoonBit's component tutorial and scala-wasm both pass `--encoding utf16` to `wasm-tools component embed`. — [MoonBit component model tutorial](https://docs.moonbitlang.com/en/latest/toolchain/wasm/component-model-tutorial.html); [VirtusLab](https://virtuslab.com/blog/scala/bringing-scala-to-server-side/)
- GC ABI pre-proposal mapping (future): `utf8` -> `(array i8)`, `utf16` -> `(array i16)`. — [component-model #525](https://github.com/WebAssembly/component-model/issues/525)

### Inferences
- Copy counts for "print a string to stdout" on WASI 0.3 with a linear-memory ABI: UTF-8 `(array i8)` = 1 guest copy (array -> scratch memory) then the host reads the buffer; UTF-16 `(array i16)` = 1 guest transcode+copy to UTF-8 bytes (stdout is `stream<u8>`, so the CM `string-encoding` option does not help - it applies to `string`-typed values only, not to `stream<u8>`/`list<u8>` payloads).
- For `string`-typed WIT params, declaring `string-encoding=utf8` with UTF-8 arrays means the guest copy is a plain byte copy and the host does validation only; declaring `utf16` with `(array i16)` is equally a plain copy on the guest side but forces host-side transcoding against UTF-8 hosts/components.
- Literal strategy options for a Binaryen-based compiler: (a) one passive data segment for all literals + `array.new_data` at first use, cached in a mutable nullable global (lazy, smallest binary, one null-check per use); (b) `array.new_fixed` in an immutable global initializer (constant expression, no runtime check, but one `i32.const` operand per byte so roughly 2+ bytes of code per string byte); (c) eager `array.new_data` for all literals in a start function. `array.new_data` cannot appear in a global initializer.
- Since TinyWhale has no JS target, stringref and JS string builtins give it nothing; a self-defined immutable `(array i8)` (optionally wrapped in a struct with cached hash/length-in-code-points) is consistent with Wasmtime maintainers' explicit advice.

### Gaps
- Exact WIT signature of the 0.3 stdout write function was only partially captured (doc comment, not the full `func` line); confirm against the final `wasi:cli@0.3.0` package.
- No measurement of `array.new_data` vs `array.new_fixed` cost in Wasmtime.

## 6. Closures and first-class functions on WasmGC

### Takeaway
The canonical representation is a GC struct whose first field is a typed function reference and whose remaining fields (or a subtype's fields) are the captured environment, invoked with `call_ref`; this is the pattern in the GC proposal's own overview, and the instructions it needs (typed function references, `call_ref`, `ref.cast`, struct subtyping) are Tier 1 and on by default in Wasmtime 47+.

### Cited Findings
- GC Overview closure example: `(type $code-f64-f64 (func (param $env (ref $clos-f64-f64)) (param $y f64) (result f64)))`, `(type $clos-f64-f64 (struct (field $code (ref $code-f64-f64))))`, concrete closure as a subtype adding captured fields; caller does `struct.get $code` then `call_ref`; the callee down-casts the environment ("The down cast for the closure environment is necessary to go from the abstract closure type to the concrete"). Requirements listed: "function pointers; (mutually) recursive function types; down casts". Other representations are allowed. — [WebAssembly/gc Overview.md, "Closures"](https://github.com/WebAssembly/gc/blob/main/proposals/gc/Overview.md)
- A built-in closure primitive (`func.bind` / `closure $t` heap type) exists only as a Post-MVP sketch. — [WebAssembly/gc Post-MVP.md](https://github.com/WebAssembly/gc/blob/main/proposals/gc/Post-MVP.md)
- Typed Function References and GC are finished proposals (WG 2024-07-10, Wasm 3.0). — [finished-proposals.md](https://github.com/WebAssembly/proposals/blob/main/finished-proposals.md)
- Wasmtime: `function-references` Tier 1 (Cranelift), `Config::wasm_function_references` under the `gc` crate feature. — [Wasmtime "Wasm Proposals"](https://docs.wasmtime.dev/stability-wasm-proposals.html); [config.rs](https://github.com/bytecodealliance/wasmtime/blob/main/crates/wasmtime/src/config.rs)
- Wasmtime 47.0.0: "The `call_indirect` instruction of `final` super types has been optimized when the GC proposal is enabled." — [Wasmtime v47.0.0 release](https://github.com/bytecodealliance/wasmtime/releases/tag/v47.0.0)
- Binaryen exposes `BinaryenCallRef` and whole-program passes that can devirtualize: GUFA "infer[s] ... when a location must hold a constant, which enables devirtualization". — [binaryen-c.h](https://github.com/WebAssembly/binaryen/blob/main/src/binaryen-c.h); [GC Optimization Guidebook](https://github.com/WebAssembly/binaryen/wiki/GC-Optimization-Guidebook)

### Inferences
- `call_ref` on a non-null typed reference needs no runtime signature check (the type system guarantees it), whereas `call_indirect` does a table bounds check plus a signature/subtype check; the 47.0.0 note shows Wasmtime had to special-case `final` types to make `call_indirect` cheap under GC. A new compiler should prefer `call_ref` and declare function types `final`.
- With closed-world Binaryen optimization, a closure whose target is statically known can be turned into a direct call and its environment struct removed by Heap2Local (section 7).

### Gaps
- No published Wasmtime benchmark comparing `call_ref` and `call_indirect` was found.

## 7. Value-type flattening on top of a GC representation

### Takeaway
Yes: Binaryen's `heap2local` pass replaces non-escaping GC allocations with one local per field and runs in the default `-O` pipeline for GC modules; with `--closed-world` further type/field/signature refinement passes and (manually) GUFA run. It is an intraprocedural escape analysis, so flattening across calls still depends on inlining or on the front end emitting multi-value directly.

### Cited Findings
- Heap2Local source header: "Find heap allocations that never escape the current function, and lower the allocation's data into locals. That is, avoid allocating a GC object, and instead use one local for each of its fields." Registered as `"heap2local", "replace GC allocations with locals"` and added in the default function optimization pipeline (`addIfNoDWARFIssues("heap2local")`). — [Binaryen Heap2Local.cpp](https://github.com/WebAssembly/binaryen/blob/main/src/passes/Heap2Local.cpp); [Binaryen pass.cpp](https://github.com/WebAssembly/binaryen/blob/main/src/passes/pass.cpp)
- Global GC passes in the default pipeline (pass.cpp): `type-refining`, `signature-pruning`, `signature-refining` (in the closed-world block), `global-refining`, `remove-unused-types`, `cfp` ("propagate constant struct field values"), `gsi` ("globally optimize struct values"), `abstract-type-refining`, `unsubtyping`, `heap-store-optimization`. — [Binaryen pass.cpp](https://github.com/WebAssembly/binaryen/blob/main/src/passes/pass.cpp)
- Guidebook: `--closed-world` enables "several more important passes"; without it, types that escape are assumed inspectable from outside and left unmodified; references may still escape, "The only thing that is disallowed is for the outside to interact with the contents of the reference". GUFA is "a heavyweight optimization and not run by default. You run it manually with `--gufa`". Suggested pipelines: `-O3 --gufa -O3`, `--type-ssa -O3 -O3 --type-merging -O3`; J2Wasm uses "6 or so" rounds; "it is always useful to do `--type-finalizing` at the very end". — [Binaryen GC Optimization Guidebook](https://github.com/WebAssembly/binaryen/wiki/GC-Optimization-Guidebook)
- CONFLICT (minor): the guidebook summary states GUFA "requires `--closed-world` to run", while Binaryen's CHANGELOG describes `--closed-world` as enabling "more optimizations in GC mode"; I did not verify in source whether GUFA is hard-gated or merely far less effective in open world. — [GC Optimization Guidebook](https://github.com/WebAssembly/binaryen/wiki/GC-Optimization-Guidebook); [Binaryen CHANGELOG](https://github.com/WebAssembly/binaryen/blob/main/CHANGELOG.md)
- Engine side: Wasmtime 50.0.0: "Cranelift's alias analysis is faster and more precise, and GC struct fields, array elements, and GC header fields now all have their own alias regions." — [RELEASES.md release-50.0.0](https://github.com/bytecodealliance/wasmtime/blob/release-50.0.0/RELEASES.md)

### Inferences
- Candidates (b) and (c) are not exclusive: a GC representation as the single semantic model, with Heap2Local (and the compiler's existing flattening for values that provably do not escape) as an optimization, keeps today's "records in locals" performance for local records while giving lists, closures and escaping records a uniform heap form.
- Closed-world mode fits a component: the only values crossing the boundary are scalars and bytes in scratch memory, so no GC type is exposed to the outside and Binaryen may rewrite all struct/array types freely.
- Nothing found indicates Cranelift itself performs escape analysis/scalar replacement of GC allocations; allocation removal must come from the toolchain (Binaryen).

### Gaps
- No documentation found on Heap2Local's handling of arrays vs structs or its limits (e.g. fixed-size arrays only); not verified.
- No published size/speed numbers for these passes on small languages.

## 8. Recommendation-relevant facts: binary size, Wasmtime collector performance, Bytecode Alliance guidance

### Takeaway
Wasmtime's default collector since 46.0.0 is a simple Cheney semi-space copying collector with bump allocation (in-wasm fast path) and no barriers, explicitly tuned for many short-lived instances and acknowledged to be behind browser engines on throughput; there are no published benchmark numbers. The Bytecode Alliance has published no how-to for targeting components from GC languages; the available guidance is scattered maintainer statements (use GC arrays for strings, mix GC with linear memory + `cabi_realloc`, GC ABI later).

### Cited Findings
- Timeline: 45.x (June 2026) "initial implementation of a copying collector for GC, which notably enables collecting cycles unlike the DRC collector"; 46.0.0 (2026-06-22) "Wasmtime's default garbage collector is now the copying collector instead of the deferred-reference-counting collector. This collector should be more performant in most situations and additionally have the ability to collect cycles" and "Wasmtime's copying collector now has an in-wasm fast path for its bump allocator"; 47.0.0 (2026-07-20) GC on by default. Latest release at time of writing: 50.0.1 (2026-10-29); 51.0.0 unreleased. — [RELEASES.md release-45.0.0](https://github.com/bytecodealliance/wasmtime/blob/release-45.0.0/RELEASES.md); [RELEASES.md release-46.0.0](https://github.com/bytecodealliance/wasmtime/blob/release-46.0.0/RELEASES.md); [v47.0.0 release](https://github.com/bytecodealliance/wasmtime/releases/tag/v47.0.0); [RELEASES.md release-50.0.0](https://github.com/bytecodealliance/wasmtime/blob/release-50.0.0/RELEASES.md)
- Collectors selectable with `-C collector=drc|null|copying`; `Collector::Auto` "Currently ... always defaults to the copying collector". DRC "cannot currently collect cycles; they will leak until the GC heap's store is dropped". Null collector "does not actually collect any garbage ... useful for incredibly short-running Wasm instances" and for measuring collector overhead. — [config.rs](https://github.com/bytecodealliance/wasmtime/blob/main/crates/wasmtime/src/config.rs); [cli-flags lib.rs](https://github.com/bytecodealliance/wasmtime/blob/main/crates/cli-flags/src/lib.rs)
- Design/performance statements (2026-07-20): "simple Cheney-style semi-space copying collector"; allocation is a bump pointer; no read or write barriers; throughput and latency "won't match" V8's/SpiderMonkey's today; tuned for many short-lived disposable instances rather than long-lived servers; collector performance has had less attention than correctness; instantiation stays around 5 microseconds with the pooling allocator. No GC benchmark numbers are given. — [Bytecode Alliance, "GC and Exceptions in Wasmtime"](https://bytecodealliance.org/articles/wasmtime-gc)
- Maintainer caveat, 2026-04-28 (fitzgen): "We're already struggling to get good performance in the face of the GC heap's sandboxed design." — [BA Zulip archive of wasmtime #13216](https://bytecodealliance.github.io/zulip-archive/stream/225357-git-wasmtime/topic/wasmtime.20.2F.20issue.20.2313216.20Enable.20Wasm.20GC.20by.20default.html)
- A semi-space collector keeps an active and an idle semi-space, i.e. the heap needs room for both. — [Bytecode Alliance, "GC and Exceptions in Wasmtime"](https://bytecodealliance.org/articles/wasmtime-gc)
- Binary size data points for a WasmGC language with no bundled runtime: Zena 37 bytes (return 1) and 351 bytes (hello-world string export). — [Zena announcement](https://justinfagnani.com/2026/09/09/zena-a-new-wasm-first-programming-language/)
- Guidance statements from Bytecode Alliance maintainers: strings -> `(array i8)`/`(array i16)` with toolchain-defined semantics (fitzgen, 2024-10); GC + linear memory + `cabi_realloc` in one module is the supported way to use WIT today (Fallin, 2025-05); for the GC ABI, experiment with `wasm-tools` only, since components using it cannot be run (fitzgen, 2025-09). — [BA Zulip, stringref](https://bytecodealliance.github.io/zulip-archive/stream/217126-wasmtime/topic/stringref.20implementation.20in.20WasmTime.html); [BA Zulip, Wasm GC and Preview 2](https://bytecodealliance.github.io/zulip-archive/stream/217126-wasmtime/topic/Wasm.20GC.20and.20Preview.202.html); [BA Zulip, component model with GC proposal](https://bytecodealliance.github.io/zulip-archive/stream/206238-general/topic/component.20model.20with.20GC.20proposal.html)
- The component-model book has language pages for MoonBit and Go/TinyGo (both linear-memory paths); no page for a WasmGC-based toolchain was found. — [component-model book, MoonBit](https://component-model.bytecodealliance.org/language-support/moonbit.html); [component-model book, Go](https://component-model.bytecodealliance.org/language-support/go.html)

### Inferences
- Trade-off summary for the three roadmap candidates, derived from the findings above:
  - (a) linear-memory values with explicit layouts: zero marshalling for lists/strings at the canonical ABI (layouts can match it), works with `realloc` natively, no dependence on Wasmtime's young GC; cost is that TinyWhale must implement its own memory management (bump/region, refcount, or a GC) and closures/records become raw pointers without engine type safety.
  - (b) WasmGC reference types: no allocator or collector to write, typed closures via `call_ref`, tiny binaries, Binaryen can remove non-escaping allocations; cost is one O(n) copy per string/list crossing into a scratch memory, dependence on a collector that Wasmtime itself describes as correctness-first, Cranelift-only (no Winch), and an ABI layer the compiler must generate itself (no wit-bindgen backend for a custom GC layout).
  - (c) locals/multi-value only: matches canonical-ABI flattening for scalars/records within flat limits, but cannot express `string`, `list`, or `stream<u8>` payloads without some memory, and cannot represent escaping closures or recursive data; viable only as an optimization layer under (a) or (b).
- For string choice under (b): immutable `(array i8)` UTF-8 minimizes work against WASI 0.3 (`stream<u8>` stdout, CM default `utf8`) and matches the pre-proposal GC ABI mapping; `(array i16)` only pays off with a JS/JVM-style host, which TinyWhale does not target.
- Short-lived CLI-style components may never trigger a collection; the null collector is an embedder option for that profile but is a host setting, not something a guest can request.

### Gaps
- No published allocation-rate or GC-pause benchmarks for Wasmtime's copying collector, and no comparison with linear-memory allocators, were found.
- No official Bytecode Alliance document titled or scoped as guidance for GC-language component toolchains was found; absence is as of the pages checked on 2026-11-14.
- Binary-size cost of the canonical-ABI glue (scratch allocator + copy loops + async stream plumbing) for a GC language is not published anywhere I found.
- WASI 0.3 guest-side async plumbing (callback vs stackful lift, `waitable-set`, stream buffer lifetimes) for a hand-written compiler backend was out of scope here and should be taken from the WASI 0.3 researcher's notes.
