# Wasmtime 50 Supports TinyWhale's GC Restart

As of 14 November 2026, Wasmtime can carry everything the restart plan asks of it, with one structural limit: WasmGC stops at the component boundary. The author's belief is confirmed for the default Cranelift compiler: GC and exception handling became default-on in **Wasmtime 47.0.0 (2026-07-20)**, and typed function references flipped in the same release ([47 release notes](https://github.com/bytecodealliance/wasmtime/blob/release-47.0.0/RELEASES.md)). Final **WASI 0.3.0 has been on by default since Wasmtime 46.0.0 (2026-06-22)**, and the latest stable release is **50.0.1 (2026-10-29)** ([46 release notes](https://github.com/bytecodealliance/wasmtime/blob/release-46.0.0/RELEASES.md); [releases page](https://github.com/bytecodealliance/wasmtime/releases)). The Component Model canonical ABI is still defined only over linear memory, and the GC ABI is an open pre-proposal whose type mapping changed as recently as 2026-11-04, so every string, list and stream payload must be copied through a linear memory the module also defines ([CanonicalABI.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md); [component-model #525](https://github.com/WebAssembly/component-model/issues/525)). The evidence supports building the restart on WasmGC structs and arrays for all language values, immutable UTF-8 `(array i8)` strings, a small scratch linear memory at the boundary, a core module wrapped by `wasm-tools component embed/new`, and execution tests that spawn a pinned `wasmtime` CLI. Two decisions cannot be settled from reading alone and need a short executed spike: whether binaryen.js 132 can express typed closures, and whether the derived minimal WASI 0.3 "hello world" actually validates and runs. Nothing in the underlying research was executed; every behaviour below is as documented or as written in source, and the report marks each inference and unverified item as such.

A note on evidence. Facts about TinyWhale come from the repository analysis in `research_notes/TinyWhale Wasmtime retargeting research/tinywhale_current_state.md` and are cited as file paths. Spec files, WIT files, Wasmtime release notes and source were read raw. Pages on wasi.dev, bytecodealliance.org and doc.rust-lang.org were read through a summarising fetch tool, so wording from them is close paraphrase unless quoted. GitHub issue trackers were mostly unreachable. In each section, paragraphs labelled **Verified** contain sourced facts, **Inference** contains reasoning from those facts, and **Recommendation** contains advice.

## GC has been default-on since Wasmtime 47, with Cranelift only

**Verified: the default flip.** The 47.0.0 notes say "Wasmtime now has the WebAssembly GC proposal enabled by default" and the same for exception handling ([47 release notes](https://github.com/bytecodealliance/wasmtime/blob/release-47.0.0/RELEASES.md)). A Bytecode Alliance post by Nick Fitzgerald dated 20 July 2026 agrees ([GC and Exceptions in Wasmtime](https://bytecodealliance.org/articles/wasmtime-gc)). The 47 notes do not mention function references; that flip is visible only in source, where the `Config::wasm_function_references` doc comment changes from "`false` by default" on the 46 branch to "`true` by default" on the 47 branch, and the default feature set becomes `WasmFeatures::WASM3` ([config.rs, release-46](https://github.com/bytecodealliance/wasmtime/blob/release-46.0.0/crates/wasmtime/src/config.rs); [config.rs, release-47](https://github.com/bytecodealliance/wasmtime/blob/release-47.0.0/crates/wasmtime/src/config.rs)). The pull request that flipped function references was not identified.

**Verified: the caveat.** The defaults hold for Cranelift only. The Winch baseline compiler marks GC and function references as unsupported, and 50.0.0 states "Winch no longer enables the GC types, exceptions, or tail-call proposals by default" ([config.rs, release-50](https://github.com/bytecodealliance/wasmtime/blob/release-50.0.0/crates/wasmtime/src/config.rs); [50 release notes](https://github.com/bytecodealliance/wasmtime/blob/release-50.0.0/RELEASES.md)). Cranelift supports GC on x86_64, aarch64, s390x, riscv64 and the Pulley interpreter ([tiers doc](https://docs.wasmtime.dev/stability-tiers.html)). `gc`, `function-references`, `exception-handling`, `tail-call` and `multi-memory` are Tier 1 ("Production Ready") proposals, which puts them inside the security policy ([proposals doc](https://docs.wasmtime.dev/stability-wasm-proposals.html); [tiers doc source](https://github.com/bytecodealliance/wasmtime/blob/release-50.0.0/docs/stability-tiers.md)). Wasmtime does not support the legacy exception encoding: `wasm_legacy_exceptions` is hidden, deprecated and "only exists for internal usage with the spec testsuite" ([config.rs, release-50](https://github.com/bytecodealliance/wasmtime/blob/release-50.0.0/crates/wasmtime/src/config.rs)).

**Verified: collectors.** Three collectors ship. The copying collector (Cheney semi-space, stop-the-world, bump allocation, no barriers, collects cycles) first appeared in 45.0.0 and has been the **default since 46.0.0**; deferred reference counting (DRC) cannot collect cycles; the null collector never collects and traps when memory runs out ([45 release notes](https://github.com/bytecodealliance/wasmtime/blob/release-45.0.0/RELEASES.md); [46 release notes](https://github.com/bytecodealliance/wasmtime/blob/release-46.0.0/RELEASES.md); [config.rs, release-50](https://github.com/bytecodealliance/wasmtime/blob/release-50.0.0/crates/wasmtime/src/config.rs)). The CLI selector is `-C collector=drc|null|copying` ([cli-flags, release-50](https://github.com/bytecodealliance/wasmtime/blob/release-50.0.0/crates/cli-flags/src/lib.rs)). The GC heap is itself built on a linear memory, and a reference "is not a native pointer, it is a 32-bit index into the GC heap's underlying linear memory" ([GC and Exceptions in Wasmtime](https://bytecodealliance.org/articles/wasmtime-gc)). The heap has its own tunables since 45.0.0, including `gc-heap-initial-size`, `gc-heap-reservation` and `gc-heap-guard-size`; the documented default reservation is 4 GiB on 64-bit hosts ([45 release notes](https://github.com/bytecodealliance/wasmtime/blob/release-45.0.0/RELEASES.md); [Config API docs](https://docs.wasmtime.dev/api/wasmtime/struct.Config.html)).

**Verified: limits and performance.** Wasmtime's own post says throughput and latency "won't match" V8 or SpiderMonkey today and that the design targets many small, short-lived instances ([GC and Exceptions in Wasmtime](https://bytecodealliance.org/articles/wasmtime-gc)). Open performance issues include no escape analysis (#9349), subtype checks not inlined (#13484) and slow funcref fields in GC objects (#9347) ([issue search](https://github.com/bytecodealliance/wasmtime/issues?q=is%3Aissue%20state%3Aopen%20label%3Awasm-proposal%3Agc%20label%3Aperformance)). Only anecdotal numbers exist. In one closed issue, a Kotlin/Wasm benchmark on `main` on 15 May 2026 reported copying 3.407, null 3.455, DRC 14.424 and Node 6.984 (units not stated) after `array.copy` fixes ([wasmtime #13279](https://github.com/bytecodealliance/wasmtime/issues/13279)). No controlled comparison with other engines and no pause-time figures were found. GC is young: a maintainer called it "not yet tier-1" on 26 May 2026 ([wasmtime #13470](https://github.com/bytecodealliance/wasmtime/issues/13470)), and GC-related security advisories were patched on 2026-10-02 (two GC heap corruption bugs, in 48.0.4 and 49.0.2) and on 2026-10-29 (type confusion and a panic, in 48.0.8, 49.0.5 and 50.0.1). One research note instead attributes the heap corruption fixes to the 29 October releases; the per-advisory dates given here follow the 48 and 49 release notes ([48 release notes](https://github.com/bytecodealliance/wasmtime/blob/release-48.0.0/RELEASES.md); [49 release notes](https://github.com/bytecodealliance/wasmtime/blob/release-49.0.0/RELEASES.md)).

**Verified: other proposals.** With Cranelift on 50, the default set is Wasm 3.0 plus wide arithmetic, which includes tail calls (default-on since 22.0.0), multi-memory and memory64 ([config.rs, release-50](https://github.com/bytecodealliance/wasmtime/blob/release-50.0.0/crates/wasmtime/src/config.rs); [22 release notes](https://github.com/bytecodealliance/wasmtime/blob/release-22.0.0/RELEASES.md)). Stack switching is Tier 3, off by default and work in progress; stringref appears nowhere in Wasmtime's proposal docs, Config or CLI flags ([proposals doc](https://docs.wasmtime.dev/stability-wasm-proposals.html)).

**Verified: release policy.** A major version ships on the 20th of each month. Releases that are multiples of 12 are LTS with 24 months of support; others get 2 months. New features are never backported ([release process](https://docs.wasmtime.dev/stability-release.html)). Wasmtime 48.0.0 (2026-08-20) is the current LTS and the first LTS with GC default-on; 51.0.0 is at rc.1 and unreleased ([48 release notes](https://github.com/bytecodealliance/wasmtime/blob/release-48.0.0/RELEASES.md); [51 release notes](https://github.com/bytecodealliance/wasmtime/blob/release-51.0.0/RELEASES.md)).

**Inference.** A module emitted for Wasmtime 47 or later with Cranelift needs no `-W` flags for structs, arrays, `i31`, `ref.cast`, `call_ref` or `try_table`. Because references are 32-bit indices, one store's GC heap is bounded by a 32-bit address space and the semi-space design leaves about half for live data; no source states a maximum, so this is derived from the design. The end-of-life dates for LTS lines (36 to about August 2027, 48 to about August 2028) are computed from the policy; the official table is JavaScript-rendered and was not read.

**Recommendation: pin 50.0.1 exactly, and re-pin deliberately.** The two research threads disagree here and the disagreement is real. The GC evidence alone favours 48 LTS for its 24-month support. The WASI 0.3 evidence favours 50 or later, because 50.0.0 synchronised component-model-async with post-0.3.0 spec changes (the `cancellable` immediate was removed, and using a stream or future handle after the other end drops now traps), and features are never backported to 48 ([50 release notes](https://github.com/bytecodealliance/wasmtime/blob/release-50.0.0/RELEASES.md)). Since the restart commits to native WASI 0.3 async, the async surface decides, and 50.0.1 is the newest release carrying both that sync and the October GC fixes. Expect to move when 51 ships: its notes describe "a large number of tweaks, adjustments, and primarily fixes for component-model-async behavior" ([51 release notes](https://github.com/bytecodealliance/wasmtime/blob/release-51.0.0/RELEASES.md)). Whether a component built with current wasm-tools loads unchanged on 48 was not tested.

## WASI 0.3.0 shipped on 11 June 2026, and a sync-lifted `run` is enough

**Verified: status.** WASI 0.3.0 was ratified by a WASI Subgroup vote and released on **2026-06-11**; 0.3.1 followed on 2026-08-11 and 0.3.2 on 2026-10-13, on a two-month train ([wasi.dev roadmap](https://wasi.dev/roadmap); [WASI releases](https://github.com/WebAssembly/WASI/releases)). 0.3.1 adopted the `map<K,V>` type and the `implements` annotation; 0.3.2's change list is housekeeping only ([component-model README](https://github.com/WebAssembly/component-model/blob/main/README.md); [WASI releases](https://github.com/WebAssembly/WASI/releases)). WASI 1.0 has no date and depends on Component Model 1.0, which needs native implementation in two browser engines ([The Road to Component Model 1.0](https://bytecodealliance.org/articles/the-road-to-component-model-1-0)). Claims of a February 2026 release or of "Wasmtime 43+" support trace to pre-release snapshots: `v0.3.0-rc-2026-02-09` is a tag, and Wasmtime 41 to 45 implemented snapshots behind `-S p3 -W component-model-async=y` ([wasi.dev P3 page](https://wasi.dev/releases/wasi-p3); [43 release notes](https://github.com/bytecodealliance/wasmtime/blob/release-43.0.0/RELEASES.md)).

**Verified: what changed.** 0.3 deletes `wasi:io`. Pollables become `future<T>`, byte streams become `stream<u8>`, and start/finish pairs become `async func` ([wasi.dev P3 page](https://wasi.dev/releases/wasi-p3)). The `wasi:cli/command` world exports `run: async func() -> result` ([run.wit at v0.3.0](https://github.com/WebAssembly/WASI/blob/v0.3.0/proposals/cli/wit/run.wit)). Standard output has no synchronous write: the signature is `write-via-stream: func(data: stream<u8>) -> future<result<_, error-code>>`, and it is not an `async func` ([stdio.wit at v0.3.0](https://github.com/WebAssembly/WASI/blob/v0.3.0/proposals/cli/wit/stdio.wit)).

**Verified: the stable ABI surface.** The features shipped in 0.3.0 and frozen against breaking changes before 1.0 are the `async` function effect, `stream` and `future` types, the `async` and `callback` canonical options, and the associated built-ins ([Text.md, gated features](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Text.md#gated-features)). Still gated and off by default in Wasmtime: stackful async lift, synchronous variants of stream and future read/write, cooperative-thread built-ins other than `thread.yield`, `error-context`, and `stream.forward` ([Text.md, gated features](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Text.md#gated-features); [Wasmtime proposals status](https://github.com/bytecodealliance/wasmtime/blob/main/docs/stability-wasm-proposals.md)). The rule that matters most to a small compiler is quoted directly: "`async` function exports may be implemented with the *sync* ABI and then call `async` function imports using the *sync* ABI," so sync code compiles to components exporting async functions without a coroutine transform ([Concurrency.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#summary)).

**Verified: the numbers a backend must encode.** `stream.new` and `future.new` return one `i64` with the readable end in the low 32 bits and the writable end in the high 32 bits ([CanonicalABI.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md#-canon-streamfuturenew)). In stable 0.3.0, `stream.read` and `stream.write` must carry `async`; they take (handle, pointer, count) and return either `0xffff_ffff` (blocked, an event follows) or a result code in the low 4 bits (completed 0, dropped 1, cancelled 2) with the element count above ([Text.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Text.md#-streamread-and-streamwrite); [CanonicalABI.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md#-canon-streamfuturereadwrite)). `waitable-set.wait` writes two `i32`s at a payload address and returns an event code: subtask 1, stream-read 2, stream-write 3, future-read 4, future-write 5 ([Text.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Text.md#-concurrency-built-ins); [CanonicalABI.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md)). A stackless async export is lifted with `async` plus `callback`; the core function returns EXIT 0, YIELD 1, or WAIT 2 with a waitable-set index in the high 28 bits, the callback has type `(func (param i32 i32 i32) (result i32))`, and the value is delivered through `task.return`, which traps if called from a sync-lifted export ([Concurrency.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#stackless-async-exports); [CanonicalABI.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md#-canon-taskreturn)). Async-lowered imports take at most 4 flat parameters, return values through a memory pointer, and return an `i32` status ([Concurrency.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#async-import-abi)). Two `context.get/set` slots exist per task for state such as a shadow-stack pointer ([Concurrency.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Concurrency.md#thread-local-storage)).

**Verified: letting wasm-tools build the component.** A backend can emit a core module and have `wit-component` wrap it. It recognises names such as `[async-lift]…`, `[callback][async-lift]…`, `[async-lower]…`, `[task-return]…`, `[waitable-set-new]`, `[waitable-set-wait]`, `[waitable-join]`, `[stream-new-N]`, `[stream-write-N]`, `[stream-drop-writable-N]`, `[future-read-N]` and `[future-drop-readable-N]` ([wit-component validation.rs](https://github.com/bytecodealliance/wasm-tools/blob/main/crates/wit-component/src/validation.rs)). These prefixes belong to the "legacy" name mangling; the embed help says the newer standard scheme "does not yet support async-related features" ([wasm-tools component.rs](https://github.com/bytecodealliance/wasm-tools/blob/main/src/bin/wasm-tools/component.rs)).

**Verified: Wasmtime behaviour.** `wasmtime run` on a component first tries the 0.3 `Command` world and calls `wasi:cli/run` concurrently, falling back to 0.2 ([run.rs](https://github.com/bytecodealliance/wasmtime/blob/main/src/commands/run.rs)). The WIT vendored in `wasmtime-wasi` on `main` is `wasi:cli@0.3.0`, and `map` and `implements` are listed as off by default ([vendored cli.wit](https://github.com/bytecodealliance/wasmtime/blob/main/crates/wasi/src/p3/wit/deps/cli.wit); [Wasmtime proposals status](https://github.com/bytecodealliance/wasmtime/blob/main/docs/stability-wasm-proposals.md)). The implementation is young: async-related security and panic fixes shipped from August through October 2026, including a native stack buffer overflow from an unvalidated callback result count ([48 release notes](https://github.com/bytecodealliance/wasmtime/blob/release-48.0.0/RELEASES.md); [49 release notes](https://github.com/bytecodealliance/wasmtime/blob/release-49.0.0/RELEASES.md)).

**Inference: the minimum "hello world".** No official WASI 0.3 hello world in WAT was found; the following is derived from the cited rules and was not executed. The component needs an exported linear memory holding the bytes; an import of `wasi:cli/stdout@0.3.0`; an export of `wasi:cli/run@0.3.0`; a sync `canon lower` of `write-via-stream` (core type `(func (param i32) (result i32))`); and the built-ins `stream.new`, `stream.write` (with `async` and memory), `stream.drop-writable`, `future.read`, `future.drop-readable`, `waitable-set.new`, `waitable.join`, `waitable-set.wait` and `waitable-set.drop`. The `run` body creates the stream, passes the readable end to `write-via-stream`, writes, and on `0xffff_ffff` joins the writable end to a set and waits for event 3; it loops until all bytes are reported, drops the writable end, reads the completion future (waiting for event 4 if blocked), and returns `i32` 0. The core `run` is lifted without `async`. Whether `realloc` can be omitted here, whether a waitable must be joined before the blocking operation starts, and the exact import module names under `wit-component` are unverified.

**Inference.** Because a sync-lifted async export holds the instance lock while blocked, such a component serves one export call at a time. That suits a CLI `run` and limits an HTTP handler. Real intra-component concurrency in stable 0.3.0 requires the callback ABI, which means the compiler must turn async functions into state machines, because the stack is not preserved between callback invocations.

**Recommendation.** Import `@0.3.0` interfaces, since that is what Wasmtime vendors; whether 0.3.2-versioned imports link against it was not verified. Do not design language semantics around `error-context`, stackful lift or `thread.*`; all are gated. Keep ABI glue isolated in the backend, because a "lazy ABI" replacing the `realloc` convention is planned as an opt-in 0.3.x option; that detail came through a summarising tool and should be re-read before being relied on ([The Road to Component Model 1.0](https://bytecodealliance.org/articles/the-road-to-component-model-1-0)).

## GC values stay inside the module; bytes cross through scratch memory

**Verified: mixing is allowed.** A core module may define GC types and linear memories together. Chris Fallin of Wasmtime wrote on 2025-05-21 that "The two coexist just fine," with WIT data passing through linear memory allocated by `cabi_realloc` ([Zulip, Wasm GC and Preview 2](https://bytecodealliance.github.io/zulip-archive/stream/217126-wasmtime/topic/Wasm.20GC.20and.20Preview.202.html)). A worked example exists: the scala-wasm fork runs a WasmGC core module inside a WASI 0.2 component on Wasmtime, built with `wasm-tools component embed` and `component new` ([VirtusLab, 2025-10-28](https://virtuslab.com/blog/scala/bringing-scala-to-server-side/)). `wit-component` validates its input with `WasmFeatures::all()`, so GC core modules are accepted ([wit-component validation.rs](https://github.com/bytecodealliance/wasm-tools/blob/main/crates/wit-component/src/validation.rs)).

**Verified: the boundary is linear-memory only.** The canonical option grammar on `main` contains string encodings, `memory`, `realloc`, `post-return`, `async` and `callback`, and no GC option ([Text.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Text.md)). The validation rules are exact: "`lower(T)` requires `memory` if `T` contains a `list` or `string`"; "`lift(T)` requires `realloc` if `T` contains a `list` or `string`"; streams with an element type require `memory` ([CanonicalABI.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md)). Records, tuples and variants flatten to core values and need no memory until the flat limits (16 parameters, 1 result) are exceeded ([CanonicalABI.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md)). The encoder fails with "module does not export a function named `cabi_realloc`" when a signature needs one ([wit-component encoding.rs](https://github.com/bytecodealliance/wasm-tools/blob/main/crates/wit-component/src/encoding.rs)).

**Verified: the GC ABI is not usable.** Issue #525, opened 2025-06-03, is still open with no milestone; on 2026-11-04 its author reported that variants with record or tuple payloads cannot be lowered unambiguously and proposed changing the mapping ([component-model #525](https://github.com/WebAssembly/component-model/issues/525)). Wasmtime has `-W component-model-gc`, whose doc says support "is _very_ incomplete", and the adapter compiler on `main` contains 69 `todo!("CM+GC")` sites ([config.rs, main](https://github.com/bytecodealliance/wasmtime/blob/main/crates/wasmtime/src/config.rs); [fact/trampoline.rs](https://github.com/bytecodealliance/wasmtime/blob/main/crates/environ/src/fact/trampoline.rs)). The July 2026 post names component-model GC integration as the next milestone to prototype ([GC and Exceptions in Wasmtime](https://bytecodealliance.org/articles/wasmtime-gc)).

**Verified: no bulk copy exists.** The WasmGC MVP has no instruction with both an array and a memory operand; `array.copy` is array-to-array and `array.new_data` reads a data segment ([GC MVP.md](https://github.com/WebAssembly/gc/blob/main/proposals/gc/MVP.md)). "More Array Constructors" (memory to new array only) is at Phase 1 and "Multibyte Array Access" at Phase 2 ([proposals README](https://github.com/WebAssembly/proposals/blob/main/README.md)). Linear memory cannot hold GC references, and the MVP has no interior pointers ([GC Overview.md](https://github.com/WebAssembly/gc/blob/main/proposals/gc/Overview.md)).

**Verified: strings.** Stringref is Phase 1, and Wasmtime maintainers said in October 2024 there were "No plans currently" to implement it; Nick Fitzgerald advised non-JS toolchains to lower strings to `(array i8)` for UTF-8 or `(array i16)` for UTF-16 and implement the semantics themselves ([Zulip, stringref in Wasmtime](https://bytecodealliance.github.io/zulip-archive/stream/217126-wasmtime/topic/stringref.20implementation.20in.20WasmTime.html)). The Component Model's default string encoding is `utf8` ([Text.md](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Text.md#canonical-abi)). The GC ABI pre-proposal maps `utf8` strings and `list<u8>` to `(array i8)` ([component-model #525](https://github.com/WebAssembly/component-model/issues/525)). For literals, `array.new_data` allocates from a passive data segment but is not permitted in constant expressions, whereas `array.new_fixed` is ([GC MVP.md](https://github.com/WebAssembly/gc/blob/main/proposals/gc/MVP.md)). Prior art splits: Guile Hoot lowers to 8-bit arrays copied at the host boundary, while MoonBit and scala-wasm pass `--encoding utf16` ([Hoot status](https://files.spritely.institute/docs/guile-hoot/latest/Status.html); [MoonBit tutorial](https://docs.moonbitlang.com/en/latest/toolchain/wasm/component-model-tutorial.html)).

**Verified: prior art.** No surveyed WasmGC toolchain ships components using a GC canonical ABI. The two closest precedents are new languages targeting Wasmtime: Zena synthesises canonical-ABI adapters in its compiler (labelled "In Progress") and reports a 351-byte string-returning hello world; Wado targets only the Component Model and WASI 0.3 and lists "GC across component boundaries" as something it is waiting on ([Zena announcement, 2026-09-09](https://justinfagnani.com/2026/09/09/zena-a-new-wasm-first-programming-language/); [zena README](https://github.com/elematic/zena); [wado README](https://github.com/wado-lang/wado)). MoonBit, which has both backends, uses its linear-memory one for components ([MoonBit tutorial](https://docs.moonbitlang.com/en/latest/toolchain/wasm/component-model-tutorial.html)).

**Inference.** The copy at each crossing is a per-element loop, O(n); its cost on Wasmtime is unmeasured. A UTF-8 `(array i8)` string printed to stdout needs one guest byte copy and no transcoding, because stdout is `stream<u8>` and the string-encoding option does not apply to byte streams; a UTF-16 string needs a transcode. A guest that only writes bytes out needs `memory` but, by the validation rules, not `realloc`; a guest that receives any string or list needs both. A bump allocator reset per call is unsafe once operations suspend, because a blocked `stream.write` holds a guest pointer; buffer lifetime must follow the operation. No source spells out that allocator consequence.

**Recommendation.** Represent strings as immutable `(array i8)` holding UTF-8. It matches Wasmtime maintainers' advice, the WASI 0.3 byte-stream interfaces, the default component encoding, and the current GC ABI draft. The last point is a forward-compatibility bet, not a guarantee, because that mapping is still changing.

## What the findings decide for TinyWhale's open questions

The repository analysis frames the starting point. Codegen is one 1,125-line file that uses binaryen.js for numeric operations only, flattens records and lists into locals, and emits a bare core module whose `_start` is both exported and the start function (`packages/compiler/src/codegen/index.ts`). No test instantiates a module; tests check `validate()` and WAT text (`tinywhale_current_state.md`). The roadmap requires one representation decision covering "records, lists, tuples, closure environments, and the host ABI together" and names three candidates (`docs/2026-01-19-functions-roadmap.md`). Everything in this section is recommendation built on the verified facts above.

**Runtime representation: choose WasmGC, with flattening demoted to an optimisation.** Of the three candidates, locals and multi-value alone cannot express strings, lists, stream payloads, escaping closures or recursive data, so it survives only as an optimisation layer. Linear-memory values would match the canonical ABI with no marshalling, but TinyWhale would have to write its own allocator or collector. WasmGC removes that work and gives typed closures: the GC proposal's own pattern is a struct whose first field is a typed function reference, with captured variables in a subtype, invoked by `struct.get` and `call_ref` ([GC Overview.md, closures](https://github.com/WebAssembly/gc/blob/main/proposals/gc/Overview.md)). Records and tuples become structs, lists become arrays, and the existing flattening is recovered by Binaryen's `heap2local` for values that do not escape. The costs are real and should be accepted knowingly: one O(n) copy per string or list crossing, a correctness-first collector, Cranelift only, and hand-generated ABI glue. The roadmap's planned next milestone, a function table with `call_indirect`, is superseded by `call_ref`; Wasmtime had to special-case `final` types to make `call_indirect` cheap under GC ([47 release notes](https://github.com/bytecodealliance/wasmtime/blob/release-47.0.0/RELEASES.md)).

**Host ABI: scratch memory plus generated glue.** One exported linear memory used only for marshalling, a `cabi_realloc` once any string or list flows inward, and resource and stream handles stored as plain `i32`. Zena and Wado made the same choice.

**Backend: run a spike before committing to binaryen.js as the emitter.** The closure pattern needs a function type and a struct type that refer to each other, which means one rec group containing both. binaryen.js can build that group with `TypeBuilder`, but its `addFunction` cannot assign a builder-defined type to a function. Whether that blocks typed closures could not be confirmed without running code, and it is the single most consequential unknown for the backend. If the spike fails, the fallback is the pattern the largest WasmGC toolchains already use: TinyWhale's own emitter (WAT text assembled by `wasm-tools parse`, or a binary encoder) with Binaryen kept as an optimiser through `readBinary` and `runPasses`. That route also removes the exception-builder gap and the dependence on npm releases that currently trail GitHub. If exceptions are needed while on binaryen.js 132, the registered `translate-to-exnref` pass is the likely bridge from its legacy builders; that is untested.

**Test architecture: add execution before rebuilding.** Keep the 31 fixtures and table-driven specs, and add three tiers: spawn `wasmtime run` on command components and assert stdout and exit status; use component `--invoke` with WAVE for exported functions; batch assertions into `.wast` files once per-process cost is measured. Avoid core-module `--invoke` for anything but scalars. Add `wasm-tools validate` on the final component as a gate independent of Binaryen and Wasmtime. Running a subset under `-C collector=null` separates collector bugs from codegen bugs.

**Dependency modernisation is small.** On 14 November 2026, npm latest was binaryen 132.0.0, biome 2.6.7, fast-check 4.10.2 and ace 14.1.1, with TypeScript and ohm-js already current (`tinywhale_current_state.md`). The 131 to 132 Binaryen change replaces `readBinaryWithFeatures`, which the current codegen does not use. Stay on 132 until 133 reaches npm, then budget for the type-enum break. New pins to add: Wasmtime 50.0.1 and wasm-tools 1.263.0 through mise, wkg through aqua or a release binary, and vendored `wasi:cli@0.3.0` WIT.

**Order of the remaining steps.** The author's plan is sound in content; the findings change its sequencing. Research (steps 4 and 5) is now as complete as reading allows, and the open items are answerable only by execution. So the next step should be a hand-written WAT hello world for `wasi:cli/run@0.3.0`, validated with wasm-tools and run on the pinned Wasmtime; it resolves the unverified ABI details and proves the toolchain end to end before any compiler code depends on it. The closure spike in binaryen.js follows, and fixes the backend. Then the execution harness, built against the hand-written component. Only then the from-scratch compiler, in this order: GC representation for records, lists and tuples; strings and print over the sync-lifted stream path; closures; and last, language-level async on the callback ABI, because it alone demands a state-machine transform. Adopting WASI 0.3 does not wait for that last step: printing one line already uses `stream`, `future` and a waitable set.

## Conclusion

The research turns the roadmap's "design required" item from an open three-way choice into a default with one named risk. WasmGC inside, bytes through a scratch memory outside, is what Wasmtime's maintainers describe as the supported path and what the two nearest peer languages already do; the alternatives either cannot represent the language's planned values or require TinyWhale to write a memory manager. The risk is concentrated in a single API gap in binaryen.js, cheap to test and with a well-trodden fallback.

The less obvious finding is about sequencing. WASI 0.3 has no synchronous stdout, so the restart's first observable behaviour, printing a line, already exercises streams, futures and waitable sets. That makes the async ABI the first thing to prove, by hand, before any compiler work, while the language's own async feature stays the last thing to build. It also sets the pinning rule: the async surface, still being tightened in every Wasmtime release through 51, should drive the version choice more than GC, which has been stable in shape since 47.
